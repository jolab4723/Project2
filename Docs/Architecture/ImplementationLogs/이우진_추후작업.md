## 1. 일본어·중국어 폰트 깨짐 (2026-08-04 발견, 추후 수정)

### 증상

언어를 JPN/CHN으로 바꾸면 글자가 깨져 보인다(□ 등). 번역 데이터 문제가 아니라 **폰트 적용 문제**다.

### 원인

`YJ_LanguageManager`는 폰트를 **보관·제공만** 한다(`GetCurrentFont()`).
실제로 텍스트에 적용하는 건 `YJ_LocalizedFont` 컴포넌트이고, 이건 **TMP 텍스트 오브젝트마다 개별로 붙여야** 한다.

```
[RequireComponent(typeof(TMP_Text))]
YJ_LocalizedFont
   Start()  -> LanguageChanged 구독
   ApplyFont() -> targetText.font = languageManager.GetCurrentFont()
```

그런데 `WJ_Act1_DropTest` 씬의 `YJ_LocalizedFont` 개수가 **0개**다. 폰트를 바꿔주는 주체가 없어서
모든 텍스트가 한/영 폰트를 그대로 쓰고, 일/중 글리프가 없어 깨진다.

`YJ_LanguageManager`의 폰트 3개 필드는 2026-08-04에 연결해뒀다(Pretendard / NotoSansJP / NotoSansSC).
이건 전제 조건이라 비어 있으면 `YJ_LocalizedFont`를 붙여도 `font != null` 검사에 걸려 아무 일도 안 일어난다.

### 해결 후보

- **A. 필요한 텍스트에 `YJ_LocalizedFont`를 붙인다** — JYJ님이 의도한 정석. 다만 다국어로 표시될 TMP 텍스트마다 일일이 붙여야 한다(스탯 팝업만 해도 행 10개 × 이름/값).
- **B. 부모 아래 TMP 텍스트를 한 번에 처리하는 컴포넌트를 새로 만든다** — `Canvas_Pupop` 같은 루트에 하나만 붙여 `GetComponentsInChildren<TMP_Text>()`로 일괄 교체. 손은 덜 가지만 의도적으로 다른 폰트를 쓰는 텍스트(로고, 숫자 전용 등)까지 덮어쓰므로 예외 처리가 필요하다.
- **C. 폰트 에셋의 Fallback 설정** — 한/영 폰트의 Fallback Font Assets에 일본어·중국어 폰트를 등록하면 TMP가 글리프 없을 때 자동 대체한다. 컴포넌트를 안 붙여도 되고 기존 폰트 지정도 안 건드린다. 다만 폰트 에셋 설정 변경이라 팀 공용 자산에 영향이 간다.

**C로 전반적인 깨짐을 없애고 필요한 곳만 A를 추가하는 조합을 권장**한다.

### 진행 전 확인 필요

- 실제로 어느 화면의 텍스트가 깨지는지(스탯 팝업 / 아이템 툴팁 / 그 외).
- C를 택하면 폰트 에셋이 팀 공용이라 사전 공유가 필요하다.

## 8. 클릭 이동 레이캐스트에 지면 레이어 마스크 없음 (BH 담당 영역, 2026-08-04 발견)

### 문제

`T_PlayerController.GetMouseDirection()`이 레이어 마스크 없이 레이캐스트를 쏜다.

```csharp
if (Physics.Raycast(ray, out RaycastHit hit))   // 마스크 없음
```

Unity 기본값이 `Physics.queriesHitTriggers = true`라 **트리거 콜라이더도 레이에 맞는다.**
그래서 Default 레이어에 트리거를 하나라도 놓으면, 그 위를 클릭했을 때 바닥 대신 트리거가 맞아
**그 방향으로 이동 명령이 제대로 나가지 않는다.**

### 실제로 겪은 사례

2026-08-04에 `BuffFieldZone`을 작업 씬에 배치했더니 그쪽으로 이동이 안 됐다(구현 로그 44번).
존을 `Ignore Raycast` 레이어로 옮겨 우회했고, `BuffFieldZone`은 `Reset()`에서 레이어를 자동으로
맞추고 `OnValidate()`에서 경고하도록 해뒀다.

### 왜 근본 해결이 필요한가

지금은 `BuffFieldZone`만 우회 처리된 상태다. 앞으로 아이템 픽업 범위, 상호작용 영역, 컷신 트리거 등
**Default 레이어 트리거를 추가할 때마다 같은 문제가 반복된다.** 매번 레이어를 기억해서 맞추는 것보다
레이캐스트 쪽에서 한 번 막는 게 맞다.

### 해결 방향

`T_PlayerController`의 레이캐스트에 지면 레이어 마스크를 준다(씬 바닥은 `Ground` 레이어를 쓰고 있음).
`QueryTriggerInteraction.Ignore`를 함께 주면 더 확실하다.

```csharp
Physics.Raycast(ray, out hit, Mathf.Infinity, groundLayerMask, QueryTriggerInteraction.Ignore)
```

### 진행 전 확인 필요

- `T_PlayerController.cs`는 BH 담당이라 사전 공유가 필요하다.
- 회피(Dodge) 방향 계산도 같은 메서드를 쓰므로 함께 확인해야 한다.

#### (1) `WBH_PlayerStatusEffectController.ApplyDotDamage`에 무적 가드 추가 — 271번

**무엇이 문제였나.** 플레이어가 받는 피해에 경로가 두 개인데, 무적 검사가 **한쪽에만** 있었다.

```
일반 피해   T_PlayerController.TakeDamage(WBH_DamageResult)     ← IsInvincible 검사 O
              if (IsInvincible || isCutSceneDamageBlocked || stateMachine.Is(PlayerState.Dead)) return;

도트 피해   WBH_BurnEffect.OnTick
              → WBH_PlayerStatusEffectController.ApplyDotDamage(damage)
                  → WBH_PlayerStatus.TakeDamage(float)          ← 검사 없음
                      → healthManager.TakeDamage(...)
```

도트는 컨트롤러를 거치지 않고 `WBH_PlayerStatus`로 직행해서 **무적 판정을 통째로 우회**했다.

**어떻게 드러났나.** 부활 패시브(Revive)를 테스트하다 발견했다. 최대 체력 20%(96.6)로 부활했는데 조작을 되찾는 시점엔 85까지 떨어져 있었다. 사망 직전에 걸린 화상이 부활 무적 10초 동안에도 계속 틱을 넣고 있었다.

| 구간 | 시각 | 수정 전 | 수정 후 |
|---|---|---|---|
| Dead | 0.00s | HP 0 | HP 0 |
| Revive | 1.45s | HP 97 | HP 97 |
| Idle(조작 복귀) | 4.35s | **HP 85** | **HP 97** |

**왜 이게 위험한가.** 도트가 조금만 세면 **부활 직후 다시 죽는다.** 그때는 `reviveCount`가 이미 0이라 그대로 사망 처리된다. 상태이상은 사망·부활 시 초기화되지 않으므로 죽기 직전에 걸린 도트가 그대로 따라온다.

**수정 내용.** `ApplyDotDamage` 첫 줄에 가드 한 줄을 넣었다. `controller`(`T_PlayerController`)는 이 클래스가 이미 `Awake`에서 들고 있어서 새 참조를 만들지 않았다.

```csharp
public override void ApplyDotDamage(float damage)
{
    if (controller != null && controller.IsInvincible)
        return;

    status.TakeDamage(damage);
}
```

**확인 요청 사항**

- **적 쪽에는 원래 같은 성격의 가드가 있다.** `WBH_EnemyStatusEffectController.ApplyDotDamage`는 첫 줄에서 `status.IsDead`를 확인한다. 플레이어 쪽에만 빠져 있던 것이라 의도적 누락인지 확인 필요.
- **`IsDead`는 일부러 넣지 않았다.** 요청 범위가 "무적 중"이었고 Dead 구간은 이미 체력이 0이라 도트가 더 깎을 게 없다. 적 쪽과 완전히 맞추려면 `IsDead`도 넣어야 한다.
- 회귀 확인: 무적이 아닐 때는 화상이 정상 감소(483 → 467). 도트 자체는 살아 있다.

#### (2) `T_PlayerController.reviveCount`가 `Start()`에서만 세팅됨

**무엇이 문제인가.** 부활 횟수를 정하는 코드가 `Start()`에 한 번만 있다.

```csharp
// T_PlayerController.cs:83  (Start)
reviveCount = PassiveSkillManager.Instance != null && PassiveSkillManager.Instance.HasRevive ? 1 : 0;
```

`PassiveSkillManager`의 패시브 레벨이 **그 뒤에 바뀌어도 `reviveCount`는 갱신되지 않는다.**

**언제 터지나.** 캠프에서 Revive 패시브를 해금했는데 **플레이어 오브젝트가 이미 스폰돼 있는 경우.** 해금은 성공하고 UI도 켜지지만 `reviveCount`는 0으로 굳어 있어서 **그 판에는 부활이 걸리지 않는다.** 스테이지를 새로 진입해 플레이어가 재스폰되면 그때부터 정상 동작한다.

2026-09-22 테스트에서 실제로 재현됐다. 해금 직후 `reviveCount`가 0이라 수동으로 1을 넣어야 테스트를 진행할 수 있었다.

**해결 방향.** `PassiveSkillManager.OnProfileChanged`를 구독해 다시 계산하면 된다. 이미 있는 이벤트다(`SetActiveProfile` / `TryApplyLevel` / `ResetAllCurrentLevels`에서 발행).

```csharp
// OnEnable
PassiveSkillManager.Instance.OnProfileChanged += RefreshReviveCount;
// OnDisable에서 해제
```

**판단이 필요한 지점.** 이미 1회를 쓴 뒤(`reviveCount == 0`) 패시브를 다시 적용하면 **부활이 다시 채워져야 하는지**가 결정 사항이다. 그대로 다시 계산하면 한 판에 여러 번 부활할 수 있다. "해금 시점에만 채운다" 같은 조건이 필요할 수 있다.
