## 2. 아이템 드랍 시스템 정리 (2026-07-24)

### 무엇을 작업했나

- `ItemGenerator`를 `MonoBehaviour`에서 순수 C# 클래스로 전환했다. 프리팹은 필드로 직접 들고 있지 않고, `ItemSystemController`가 생성자로 주입한다.
- `ItemSystemController`의 드랍 메서드들에서 `Quaternion rotation` 인자를 전부 제거했다. 내부적으로 `ItemGenerator.DropGeneratedItem()`을 호출할 때는 `Quaternion.identity`를 고정으로 넘긴다.
- `ItemSystemController`에 `DropGeneratedItem(ItemDefinitionSO, Vector3)` 오버로드를 추가해, 확률 롤 없이 특정 아이템을 그대로 드랍할 수 있게 했다.
- `ItemManager`의 `DropItem()`을 `DropRandomItem(EnemyGrade, Vector3)`으로 개명하고, `DropSpecificItem(ItemDefinitionSO, Vector3)`을 추가했다.
- `ItemSystemController`에 `spawnRadius`(수평 반경 랜덤 분산)와 `spawnHeightOffset`(바닥에 반쯤 묻히지 않도록 y축으로 띄우는 값, 기본 0.5)을 추가해 드랍 위치 계산에 반영했다.
- 리팩터링 도중 발견한 버그 2건을 같이 고쳤다: `ItemManager.DropSpecificItem()`이 존재하지 않는 `grade`를 참조하던 것, `ItemSystemController`의 SO 기반 오버로드가 전달받은 아이템을 무시하고 `GetRandomItemSO(grade)`로 랜덤 롤을 하던 것.
- `TestButtonController`는 곧 사용하지 않을 예정이라 `lastDropped`/`OnClickGetItem()`/`RefreshGetItemButton()`을 제거했다. 이로 인해 `Assets/SW/TEST/RandomDrop/SwTestButtonModeSwitcher.cs`가 `OnClickGetItem()`을 더 이상 찾지 못해 깨졌으며, 해당 파일은 삭제했다.
- `Assets/SW/TEST/RandomDrop/SwTestRandomDropAcquireTester.cs`에서 더 이상 존재하지 않는 `ItemDropTester`/`ItemGenerator` 관련 레거시 폴백 코드를 제거했다.
- `Assets/WJ_TestPlace/Script/Item/ItemGenerate/ItemDropTester.cs`(테스트 전용, 미사용)를 삭제했다.

## 4. 플레이어 스탯-전투 시스템 통합 (2026-07-27)

### 무엇을 작업했나

- `WJ_Act1_DropTest`(SW의 `Act1_DropTest`를 복제해온 씬)의 실제 플레이어 `Fighter`는 `T_PlayerController`/`WBH_PlayerStatus` 등 우병헌 팀원의 WBH 전투 시스템을 쓰고 있었고, WJ 스탯 시스템(`PlayerStatManager` 등)은 `WJ_StatSystemTestScene`에만 존재해 서로 연결되어 있지 않았다. `WBH_ICombatStatus`(`WBH_PlayerStatus`가 구현)가 `WBH_CombatManager`의 데미지 계산에서 플레이어·적 공용 접점으로 쓰이고 있어, `WBH_PlayerStatus` 내부 값의 출처만 WJ 스탯 시스템으로 바꾸는 어댑터 방식으로 통합했다 (사용자 확정 방향).
- `WBH_PlayerStatus.cs`(우병헌 팀원 파일, 작업 허락받음)를 수정: `MaxHealth`/`AttackPower`/`DefensePower`/`CritRate`/`CritMult`/`AttackSpeed`/`MoveSpeed`/`Fire·Ice·ElectricBonus`는 같은 GameObject의 `PlayerStatManager.Stat` 값을 반환하도록 바꾸고, 없으면 기존 Fallback 필드로 그대로 동작한다 (`Fighter`/`Gunner` 프리팹과 `TestStage`, SW `Act1_DropTest`처럼 WJ 스탯 클러스터가 없는 곳도 계속 정상 동작).
- 단위 변환 처리: WJ 스탯은 치명타 확률/치명타 피해/속성 보너스를 퍼센트 숫자(예: 5.0 = 5%)로 갖는데 `WBH_CombatManager`는 분수(0.05)·배율(1.10)을 기대해서, 그대로 넘기면 치명타율이 항상 100%가 되는 문제가 있었다. `PercentToFraction`/`PercentToMultiplier`로 변환했다.
- `TakeDamage()`/`Heal()`/`CurrentHp`/`IsDead`는 `PlayerHealthManager`로 위임하고, 기존 `OnHpChanged`/`OnDead` 이벤트는 `PlayerHealthManager`의 이벤트를 중계해서 시그니처를 그대로 유지했다.
- `T_PlayerController.Awake()`가 `status.MoveSpeed`를 읽는 시점에 `PlayerStatManager`의 Awake가 아직 안 끝났을 수 있어(같은 오브젝트 내 Awake 순서 비보장), 스탯 매니저 참조를 지연 해석(lazy resolve)하도록 했다. `PlayerHealthManager.MaxHealth`가 0인 초기 시점(Start 전)을 사망으로 오판해 `T_PlayerCombat`이 멈추는 것도 막았다.
- `Fighter`에 `PlayerLevelManager`/`PlayerBuffManager`/`PlayerEquipManager`/`PlayerStatManager`/`PlayerHealthManager`/`PlayerManaManager`/`ItemTriggerManager` 7개를 추가하고, `PlayerLevelManager.statDataJson`, `PlayerEquipManager`/`PlayerStatManager`의 `equipmentSystem`(기존 `InventoryRuntime`의 것 재사용, 새로 안 만듦)까지 배선했다. Undo 그룹 하나로 묶어서 필요시 한 번에 되돌릴 수 있게 했다.
- 이동속도 미적용 버그를 진단·수정: `T_PlayerController.cs`가 `agent.speed *= status.MoveSpeed`를 `Awake()`에서 딱 한 번만 실행해서, 레벨업 등으로 스탯이 바뀌어도 실제 이동속도(`NavMeshAgent.speed`)는 갱신되지 않고 있었다. `T_PlayerController.cs`는 수정하지 않고, `WBH_PlayerStatus`가 `PlayerStat.OnStatChanged`를 구독해서 스탯이 재계산될 때마다 `T_PlayerController.SetMoveSpeed(Stat.moveSpeed)`를 호출하도록 했다 (절대값 적용 - 사용자 확정 방향). `Initialize()`(= `T_PlayerController.Start()`) 시점에 구독해서 Awake 순서 문제도 같이 피했다.
- `PlayerStatManager`에 `[ContextMenu("전체 스탯 로그 출력")]`인 `LogAllStats()`를 추가했다. 최종 스탯 15개 전부와 레이어별(캐릭터/장비/버프/패시브) 기여분을 콘솔에 출력하며, 0인 기여분은 생략한다.

### 팀과 상의할 내용

- `baseCritMult`(예: 레벨1 10.0)를 "+10%"(배율 1.10)로 해석했다. "10배"가 의도였다면 `WBH_PlayerStatus.PercentToMultiplier` 한 줄만 바꾸면 된다.
- WBH 폴백 기본값(`maxHp = 100` 등)과 WJ 레벨1 데이터(`maxHealth = 10`)의 스케일 차이가 커서, 스탯 시스템 적용 후 체력이 100 → 10으로 체감상 크게 줄었다. 밸런스 의도인지 확인이 필요하다.
- `AttackSpeed`는 어댑터까지는 값이 오지만 실제 공격 쿨다운에 쓰는 코드가 아직 없다 (이동속도와 같은 상태였던 것 발견, 아직 미해결).
- 테스트 키 트리거 3개(`BuffTestKeyTrigger`/`UniqueEffectTestTrigger`/`ManaTestKeyTrigger`)는 WBH 입력과 충돌할 수 있어 `Fighter`에 추가하지 않았다. 필요 여부 확인이 필요하다.

## 7. 아이템 ID Excel 파이프라인 int→string 전환 (2026-07-27)

### 무엇을 작업했나

- 저장소 밖에서 별도로 관리하는 아이템 라벨 번역 파일 작업 중 itemId 표기 오류(자릿수 밀림)를 발견한 것을 계기로, 6번 항목에서 임시로 `int.ToString("D8")`로 앞자리 0을 보정하던 방식 자체를 재검토했다. itemId는 연산에 쓰이지 않는 순수 식별 코드라 애초에 숫자가 아니라 문자열로 다루는 게 맞다고 판단해 파이프라인 중간 계층을 전부 문자열로 바꿨다.
- `ItemDataTableModel.cs`의 `ArmorDefinitionRow`/`WeaponDefinitionRow`/`PotionDefinitionRow.itemId`를 `int`에서 `string`으로 변경했다.
- `ItemDataTableSOImporter.cs`의 `CreateOrUpdateBase`도 `itemId` 매개변수를 `string`으로 바꿔, 숫자 변환 없이 엑셀에 적힌 텍스트를 그대로 쓰도록 했다. 8자리가 아니면 경고를 남기는 검증도 추가해, 이번에 발견한 것 같은 자릿수 오타를 임포트 시점에 바로 알 수 있게 했다.
- 프로젝트 `Assets/Resources/DataFiles/ItemData/1. ExcelFile/ItemDataTable.xlsx`의 itemId 셀을 전부 텍스트 서식(`"01000001"` 형태)으로 바꾸고, 1행 타입 힌트도 `int`→`string`으로 맞췄다.
- Excel→JSON→SO 전체 파이프라인을 실제로 재실행해서, 기존 7개 자산을 새로 만들지 않고 같은 GUID로 정확히 찾아 갱신하는지 검증했다. 재실행 전후 GUID 7개가 완전히 동일했고, 6번 항목에서 고친 `견고한 갑옷`의 `armorType=Armor`도 그대로 유지됐다.
