## 2. 아이템 드랍 시스템 정리 (2026-07-24)

### 무엇을 작업했나

- `ItemGenerator`를 `MonoBehaviour`에서 순수 C# 클래스로 전환했다. 프리팹은 필드로 직접 들고 있지 않고, `ItemSystemController`가 생성자로 주입한다.
- `ItemSystemController`의 드랍 메서드들에서 `Quaternion rotation` 인자를 전부 제거했다. 내부적으로 `ItemGenerator.DropGeneratedItem()`을 호출할 때는 `Quaternion.identity`를 고정으로 넘긴다.
- `ItemSystemController`에 `DropGeneratedItem(ItemDefinitionSO, Vector3)` 오버로드를 추가해, 확률 롤 없이 특정 아이템을 그대로 드랍할 수 있게 했다.
- `ItemManager`의 `DropItem()`을 `DropRandomItem(EnemyGrade, Vector3)`으로 개명하고, `DropSpecificItem(ItemDefinitionSO, Vector3)`을 추가했다.
- `ItemSystemController`에 `spawnRadius`(수평 반경 랜덤 분산)와 `spawnHeightOffset`(바닥에 반쯤 묻히지 않도록 y축으로 띄우는 값, 기본 0.5)을 추가해 드랍 위치 계산에 반영했다.
- 리팩터링 도중 발견한 버그 2건을 같이 고쳤다: `ItemManager.DropSpecificItem()`이 존재하지 않는 `grade`를 참조하던 것, `ItemSystemController`의 SO 기반 오버로드가 전달받은 아이템을 무시하고 `GetRandomItemSO(grade)`로 랜덤 롤을 하던 것.
- `TestButtonController`는 곧 사용하지 않을 예정이라 `lastDropped`/`OnClickGetItem()`/`RefreshGetItemButton()`을 제거했다. 이로 인해 `Assets/SW/TEST/RandomDrop/SwTestButtonModeSwitcher.cs`가 `OnClickGetItem()`을 더 이상 찾지 못해 깨졌으며, 해당 파일은 삭제했다.
- `Assets/SW/TEST/RandomDrop/SwTestRandomDropAcquireTester.cs`에서 더 이상 존재하지 않는 `ItemDropTester`/`ItemGenerator` 관련 레거시 폴백 코드를 제거했다.
- `Assets/WJ_TestPlace/Script/Item/ItemGenerate/ItemDropTester.cs`(테스트 전용, 미사용)를 삭제했다.

## 4. 플레이어 스탯-전투 시스템 통합 (2026-07-27)

### 무엇을 작업했나

- `WJ_Act1_DropTest`(SW의 `Act1_DropTest`를 복제해온 씬)의 실제 플레이어 `Fighter`는 `T_PlayerController`/`WBH_PlayerStatus` 등 우병헌 팀원의 WBH 전투 시스템을 쓰고 있었고, WJ 스탯 시스템(`PlayerStatManager` 등)은 `WJ_StatSystemTestScene`에만 존재해 서로 연결되어 있지 않았다. `WBH_ICombatStatus`(`WBH_PlayerStatus`가 구현)가 `WBH_CombatManager`의 데미지 계산에서 플레이어·적 공용 접점으로 쓰이고 있어, `WBH_PlayerStatus` 내부 값의 출처만 WJ 스탯 시스템으로 바꾸는 어댑터 방식으로 통합했다 (사용자 확정 방향).
- `WBH_PlayerStatus.cs`(우병헌 팀원 파일, 작업 허락받음)를 수정: `MaxHealth`/`AttackPower`/`DefensePower`/`CritRate`/`CritMult`/`AttackSpeed`/`MoveSpeed`/`Fire·Ice·ElectricBonus`는 같은 GameObject의 `PlayerStatManager.Stat` 값을 반환하도록 바꾸고, 없으면 기존 Fallback 필드로 그대로 동작한다 (`Fighter`/`Gunner` 프리팹과 `TestStage`, SW `Act1_DropTest`처럼 WJ 스탯 클러스터가 없는 곳도 계속 정상 동작).
- 단위 변환 처리: WJ 스탯은 치명타 확률/치명타 피해/속성 보너스를 퍼센트 숫자(예: 5.0 = 5%)로 갖는데 `WBH_CombatManager`는 분수(0.05)·배율(1.10)을 기대해서, 그대로 넘기면 치명타율이 항상 100%가 되는 문제가 있었다. `PercentToFraction`/`PercentToMultiplier`로 변환했다.
- `TakeDamage()`/`Heal()`/`CurrentHp`/`IsDead`는 `PlayerHealthManager`로 위임하고, 기존 `OnHpChanged`/`OnDead` 이벤트는 `PlayerHealthManager`의 이벤트를 중계해서 시그니처를 그대로 유지했다.

## 35. 고유 효과에 버프 정의 인라인화 (BuffSpec / IBuffSource 도입) (2026-08-03)

### 무엇을 작업했나

- 사용자가 "UE_ 에셋 하나에서 이름·아이콘·설명·발동 조건·발동 효과를 다 설정하고, Buff To Apply는 중첩 규칙만 남기면 어떨까"라고 제안했다. 조사해보니 실제로 중복이 있었다: 이름·설명이 UE_와 버프 에셋 양쪽에 나뉘어 있었고, 버프 에셋 7개 중 5개가 특정 고유 효과 하나만을 위해 존재해 분리의 실익이 없었다.
- 다만 **"중첩 규칙만 담은 프리셋을 공유"하는 형태는 위험**하다는 점을 발견해 먼저 알렸다. `PlayerBuffManager`가 `activeBuffs.Find(b => b.definition == def)`처럼 **버프 에셋 참조 자체를 식별 키**로 쓰고 있어서, 프리셋을 여러 효과가 공유하면 한쪽을 걸었을 때 다른 쪽이 갱신·제거되는 문제가 생긴다. `duration`도 효과마다 달라(3/5/10/영구) 중첩 규칙 쪽에 두기 부적합했다.
- 사용자가 "아이템 고유 효과가 아닌 곳(포션·스킬·적 디버프)에서도 버프를 걸 계획"이라고 확인해줘서, 버프 정의를 한쪽으로 몰지 않고 **공통 payload를 추출해 양쪽이 공유**하는 구조로 정했다.

### 설계

```
BuffSpec (신규, 직렬화 클래스 - 에셋 아님)
   statEffects[] / duration / stackBehavior / maxStack
        ↑                              ↑
BuffDefinitionSO                  UniqueEffectSO 서브클래스
(포션·스킬·적 디버프용 독립 에셋)   (BuffSpec을 인라인 보유)
        ↘                              ↙
            IBuffSource (신규 인터페이스)
                    ↓
            PlayerBuffManager
```

- `IBuffSource`를 구현한 **객체의 참조**가 버프 식별 키가 된다. UE_ 에셋과 `BuffDefinitionSO` 에셋 모두 각자 고유한 객체라 충돌이 원천적으로 없다.
- `BuffDefinitionSO`는 **필드 배치를 그대로 두고** 인터페이스만 덧붙였다. 기존 버프 에셋 7개의 직렬화 데이터가 안 깨져서 마이그레이션 위험을 크게 줄였다.
- 고유 효과 아이콘은 사용자 결정에 따라 **그 효과가 붙은 아이템의 아이콘을 그대로 사용**한다. `UniqueEffectSO.icon` 필드를 추가하되 손으로 채우지 않고, `ItemDataTableSOImporter`의 아이콘 연결 단계가 아이템 아이콘을 복사해준다(한 효과가 아이콘이 다른 여러 아이템에 붙어 있으면 경고).
- `effectDescription`/`coefficients`와 `statEffects`는 사용자 결정에 따라 **분리 유지**했다. 자동 대입으로 합치면 복합 문구의 순서 제어가 어려워진다.

- 파티 후보는 `PlayerBuffManager.All`이다(각 매니저가 Awake에서 자신을 등록). 순회 중 목록이 바뀔 수 있어(사망·스폰) 역순 인덱스로 돌고, null 항목을 걸러낸다.

**`BuffFieldZone.cs` (신규, 런타임)**

영역 안에 있는 동안 버프/디버프를 유지하는 트리거 존.

- `OnTriggerEnter`에 적용, `OnTriggerExit`에 제거. 콜라이더가 자식에 있어도 되도록 `GetComponentInParent<PlayerBuffManager>()`로 찾는다.
- 안에 있는 대상을 `HashSet`으로 들고 있어서, 캐릭터에 콜라이더가 여러 개여도 **중복 적용되지 않고** 나갈 때 정확히 그 대상에게서만 뺀다.
- `removeOnExit`을 끄면 나가도 유지된다(제단처럼 한 번 받고 끝나는 경우).
- `removeWhenZoneDisabled`로 존이 꺼지거나 파괴될 때 안에 있던 대상의 버프를 정리한다. 안 그러면 존이 사라져도 버프가 영구히 남는다.
- `Reset()`에서 콜라이더를 자동으로 `isTrigger`로 맞추고, 씬 뷰에 영역 기즈모를 그린다.

### 설계 판단

- **존은 "들어온 대상"에게만 적용한다.** 파티 전체 범위를 존에 넣으면 한 명이 나갈 때 전원에게서 뺄지 말지가 애매해지고, "아무도 안 남았을 때만 해제" 같은 추가 상태 관리가 필요해진다. 파티 범위가 필요한 건 이벤트 쪽이라 그건 `BuffTargeting`이 담당한다.

### C. 고유 효과 중복 발동 정책(`duplicatePolicy`) 신설

**요청** — 쿨타임 중에 같은 유물을 하나 더 획득하면 효과가 또 발동하는 것 같으니, 고유 효과 설정으로 동명 효과의 중복 발동 여부를 정할 수 있게 해달라.

`TriggeredBuffUniqueEffectSO`에 정책을 추가했다.

| 값 | 동작 |
|---|---|
| `ShareCooldown` (기본) | 보유 개수와 무관하게 효과 하나로 취급. 한 번 발동하면 나머지 사본도 같이 쿨타임에 들어간다. |
| `PerItem` | 아이템 사본마다 쿨타임을 따로 센다. 보유 개수만큼 발동한다. |

- 쿨타임 상태를 단일 `lastTriggerTime` 하나에서 **공유용 float + `instanceId` 키 딕셔너리**로 나눴다. `PerItem`이고 소유 아이템을 알 수 있을 때만 아이템별로 나누고, 소유자를 모르는 호출(`UniqueEffectTestTrigger`가 `OnTrigger(null)`로 부른다)은 공유 쿨타임으로 처리한다.
- 버려진 아이템 기록이 쌓이지 않도록 발동 시점에 쿨타임이 끝난 항목을 정리한다(끝난 항목은 지워도 판정 결과가 같다).
- `IsReady`/`RemainingCooldown` 프로퍼티는 소유 아이템을 받아야 해서 `IsReadyFor(ItemInstance)` / `GetRemainingCooldown(ItemInstance)` 메서드로 바꿨다. 이 둘은 SO 내부에서만 쓰고 있어 외부 영향은 없었다.
- 인스펙터 값만 두면 엑셀 재변환 때 초기화되므로 파이프라인에도 넣었다: `UniqueEffectTable.xlsx`에 `duplicatePolicy` 컬럼(`cooldownSeconds` 뒤), `UniqueEffectTableRow.duplicatePolicy`, 임포터 `ApplyRow` 반영. 기존 7행은 `ShareCooldown`으로 기입했다.

## 47. 조건부 상시 고유 효과를 체력 전용에서 임의 스탯 조건으로 일반화 (2026-08-05)

### 무엇을 작업했나

**요청** — `healthThresholdPercent`처럼 체력 전용 컬럼으로 조건을 만들면, 나중에 공격력 등 다른 스탯 조건이 필요할 때마다 컬럼을 계속 늘려야 해서 비효율적이다. 특정 스탯이 얼마 이상/이하인지를 설정으로 입력할 수 있게 해달라.

`HealthThresholdBuffUniqueEffectSO`(체력 % 전용)를 `StatThresholdBuffUniqueEffectSO`(임의 스탯 + 비교 연산자 + 기준값)로 일반화했다.

### 클래스/파일 리네임 (GUID 보존)

`AssetDatabase.RenameAsset`으로 리네임해 스크립트 GUID를 유지했다(삭제 후 재생성이 아님 - 재생성하면 기존 에셋의 타입 참조가 끊긴다).

- `HealthThresholdBuffUniqueEffectSO.cs` → `StatThresholdBuffUniqueEffectSO.cs`
- `HealthThresholdRunner.cs` → `StatThresholdRunner.cs`

### 신설한 타입

```csharp
public enum StatReference
{
    CurrentHealthPercent, CurrentManaPercent,   // 현재/최대가 있는 리소스라 %로 비교
    AttackPower, DefensePower, MoveSpeed, AttackSpeed, CritRate, CritMult,
    Cdr, MpRegen, MaxMana, Pen, SkillRange, FireBonus, IceBonus, ElectricBonus, // PlayerStat 최종값 그대로 비교
}

public enum ComparisonOperator { GreaterOrEqual, LessOrEqual }
```

`StatThresholdBuffUniqueEffectSO`는 `referenceStat` / `comparisonOperator` / `thresholdValue` 세 필드로 조건을 표현한다. 체력/마나는 현재·최대 개념이 있어 %로, 나머지는 `PlayerStat`의 최종 계산값(캐릭터+장비+버프+패시브 합산 후) 그대로 비교한다.

`StatThresholdRunner`는 `referenceStat`에 따라 구독 대상을 다르게 잡는다.

| referenceStat | 구독 이벤트 |
|---|---|
| `CurrentHealthPercent` | `PlayerHealthManager.OnHealthChanged` |
| `CurrentManaPercent` | `PlayerManaManager.OnManaChanged` |
| 그 외 (최종 스탯) | `PlayerStatManager.Stat.OnStatChanged` (장비/버프/레벨/패시브 재계산마다 발행) |

기존에는 `IsReady`/필드 하나로 켜고 끄던 걸, `TryGetValue(out float)`로 값을 읽고 `comparisonOperator`로 판정하는 구조로 바꿨다. 대상 매니저의 Instance가 아직 없을 때(Awake 순서 문제)를 대비해 기존과 동일하게 `Start()`에서 구독을 재시도한다.

### 데이터 파이프라인 반영

`UniqueEffectTable.xlsx`의 `healthThresholdPercent` 컬럼을 `referenceStat` / `comparisonOperator` / `thresholdValue` 3컬럼으로 교체했다. 기존 유일한 사용처인 `UE_SturdyArmor`(체력 50% 이하 → 이동속도 +50%)를 `effectType=StatThresholdBuffUniqueEffectSO`, `referenceStat=CurrentHealthPercent`, `comparisonOperator=LessOrEqual`, `thresholdValue=50`으로 마이그레이션했다. `UniqueEffectTableModel`/`UniqueEffectTableSOImporter`/`UniqueEffectTableExcelToJson`의 관련 분기와 `nameof` 참조를 전부 새 타입명으로 갱신했다.

작업 중 openpyxl 실수를 하나 잡았다: `ws.cell(row, col, value=None)`은 "값을 지운다"가 아니라 "값을 건드리지 않는다"로 동작해서, 다른 효과 타입 행에 남아있던 잔여값이 안 지워지는 문제가 있었다. `.value = None`으로 직접 대입하는 방식으로 고쳐서 반영했다.

## 50. 공격 시 고유 효과 발동(OnDamageDealt/OnCrit) 연결, 테스트 도구, 허수아비 제작 (2026-08-05)

### 무엇을 작업했나

"공격을 했을 때 효과가 발동" 기능을 구현했다. 실제 데미지가 적용되는 유일한 지점인 `WBH_CombatManager.ProcessDamage()`(BH 소유, `Assets/WBHTest/Scripts/Combat/WBH_CombatManager.cs`)에 `ItemTriggerManager.Fire(OnDamageDealt/OnCrit)` 호출을 추가했다.

```csharp
request.Target.TakeDamage(result);

// 플레이어가 가한 피해일 때만 플레이어 장착템의 발동형 고유 효과를 건드린다.
if (request.Attacker is T_PlayerController)
{
    ItemTriggerManager.Instance?.Fire(TriggerCondition.OnDamageDealt);
    if (isCritical)
        ItemTriggerManager.Instance?.Fire(TriggerCondition.OnCrit);
}
```

근접(`SectorAttack`)과 원거리(투사체) 공격이 만든 `WBH_DamageRequest`가 전부 이 메서드로 모이므로 한 곳만 고치면 됐다. 이 매니저는 플레이어/적 전투 양쪽이 공유해서 쓰므로, `request.Attacker`가 플레이어일 때만 발동하도록 타입 검사로 걸렀다.

### 발견 및 수정한 버그: Attacker 타입 검사 오류

처음엔 `request.Attacker is T_PlayerCombat`로 검사했는데, 실제 Play 모드 테스트에서 데미지는 들어가는데 고유 효과가 전혀 발동하지 않는 걸 발견했다. 원인은 `T_PlayerCombat.CreateDamageRequest()`가 `WBH_DamageRequest`의 Attacker 자리에 `this`가 아니라 필드 `controller`(실제 타입 `T_PlayerController`, 같은 오브젝트의 다른 컴포넌트)를 넘기고 있었던 것. `request.Attacker is T_PlayerController`로 고쳐서 해결했다.

## 51. 공격속도 스탯을 실제 애니메이션 재생 속도에 실시간 반영 (2026-08-05)

### 무엇을 작업했나

`PlayerStatManager.Stat.attackSpeed`(장비/버프/레벨/패시브 합산 공격속도)가 이미 `WBH_PlayerStatus.AttackSpeed` 프로퍼티를 통해 올바르게 노출되고 있었지만, 그 값이 바뀔 때 실제 공격 애니메이션 재생 속도(`Animator`의 `"AttackSpeed"` float 파라미터)에는 반영되지 않는 문제를 고쳤다.

**원인**: 이동속도는 `WBH_PlayerStatus.SubscribeStatChanges()`에서 `Stat.OnStatChanged`를 구독해 재계산마다 `ApplyMoveSpeedToController()`로 다시 밀어주는데, 공격속도는 이 구독이 없었다. `WBH_PlayerAnimation.Start()`가 게임 시작 시점에 `SetAtkAnimationSpeed(1)`을 딱 한 번 불러서(내부적으로 `status.AttackSpeed`를 즉시 읽어 반영) 최초 값만 맞고, 이후 장비 교체·버프·레벨업으로 공격속도가 바뀌어도 애니메이션 재생 속도는 그대로 멈춰 있었다.

**수정 (`Assets/WBHTest/Scripts/Player/WBH_PlayerStatus.cs`, BH 소유 파일)**: 이동속도와 같은 패턴으로 `ApplyAttackSpeedToAnimation()`을 추가해 `Stat.OnStatChanged` 구독 목록에 넣었다.

```csharp
private void ApplyAttackSpeedToAnimation()
{
    if (!UseStatManager) return;
    OnAtkSpeedChanged?.Invoke(AttackSpeed);
}
```

`WBH_PlayerAnimation.SetAtkAnimationSpeed`(기존 코드, 수정 안 함)가 이 이벤트를 구독해 `animator.SetFloat("AttackSpeed", status.AttackSpeed)`를 그대로 호출하므로, 이벤트만 더 자주 발행되게 만들면 됐다.

### 버그 수정: 아이콘이 흰색으로 덮여 보이던 문제 (같은 날)

지속시간 표시 오버레이(`DurationFill`)를 "남은 시간 비율"로 채웠는데, 이 오버레이에 스프라이트가 없어(기본 흰 사각형) `fillAmount=1`이면 아이콘 전체가 35% 불투명 흰색으로 덮이는 구조였다. 그런데:
- **영구 지속 버프**(이 프로젝트 대부분의 버프)는 항상 `fillAmount=1` → 항상 흰색으로 덮임
- **시간제 버프**도 방금 걸었을 때(`remaining=duration`)는 `fillAmount=1` → 처음 볼 때부터 흰색으로 덮임

즉 대부분의 경우에 아이콘이 흰색 오버레이에 덮여 하얗게 보이는 게 사실상 기본 상태였다. "남은 시간"이 아니라 "경과 시간"을 덮는 방식으로 뒤집어서 고쳤다 — 방금 걸렸을 때(경과 0)는 안 덮여서 선명하게 보이고, 만료가 가까워질수록 서서히 덮여 경고 역할을 하며, 영구 버프는 애초에 전혀 덮지 않는다(`fillAmount=0` 고정).

- [x] Play 모드 재검증: 영구 버프 `fillAmount=0.00`, 방금 건 시간제 버프(라이트세이버) `fillAmount=0.00`(적용 직후) → 시간 경과 후 `1.00`에 가깝게 증가(만료 임박) 확인

### 추가: 위 수정 후에도 아이콘이 회색으로 덮여 보이던 문제 (2026-08-10)

위 `fillAmount` 방향 수정만으로는 실제로 해결되지 않았다. 수치(`fillAmount`, `sprite` 등 컴포넌트 프로퍼티)만 확인하고 실제 화면을 스크린샷으로 보지 않은 채 완료로 판단한 게 원인이었다 — 이후 실제 스크린샷과 픽셀 단위 색상 대조로 재검증해서 서로 다른 원인 3개를 모두 찾아 고쳤다.

1. **`Icon` 자식의 RectTransform 앵커가 깨져 있었다**: `anchorMin/anchorMax`가 (0,0)-(1,1) 스트레치가 아니라 (0.5, 0.5) 점 앵커에 `anchoredPosition`이 (-960, -540) 같은 큰 값으로 박혀 있어서, 실제로는 화면 밖(예: y좌표가 음수)에 렌더링되고 있었다. `Border`/`DurationFill`은 정상 위치에 남아 있어서 화면에는 "테두리만 있고 아이콘은 없는" 것처럼 보였다. 언제 이렇게 틀어졌는지는 특정하지 못했다(이전 세션의 프리팹 스테이지 편집 과정에서 발생한 것으로 추정). (0,0)-(1,1) 스트레치 + offset ±3으로 재설정.
2. **`DurationFill`의 Image Type이 프리팹에 `Sliced`로 저장돼 있었다**: 스크립트는 `fillAmount`만 설정하고 `Type`은 프리팹 기본값을 그대로 썼는데, 실제 필요한 값은 `Filled`(Radial360)였다. `Sliced` 상태에서는 `fillAmount`가 전혀 영향을 못 주고 항상 100% 불투명 사각형으로 렌더링된다 — 이게 계속 "회색 사각형"으로 보인 직접 원인.
3. **Type을 `Filled`로 고친 뒤에도 여전히 안 고쳐졌다**: `DurationFill`의 `sprite`가 `null`인 상태로 Radial360 Filled를 쓰면 `fillAmount` 값(0이든 0.5든)과 무관하게 항상 꽉 찬 사각형으로 렌더링되는 것을 스크린샷 대조로 확인했다. Unity 내장 UI 스킨 스프라이트(`UISprite`/`Background`)는 모서리가 둥글고 알파가 있어 방사형 채우기에 안 맞아서, 별도로 완전 불투명 흰색 8x8 스프라이트(`Assets/WJ_TestPlace/Prefeb/UI/BuffFillWhite.png`)를 만들어 `DurationFill.sprite`에 연결했다.

세 가지 모두 `BuffIconSlot.prefab`에 직접 반영(프리팹 스테이지에서 수정 후 저장)했고, 스크립트(`BuffIconSlot.cs`)는 변경하지 않았다.
