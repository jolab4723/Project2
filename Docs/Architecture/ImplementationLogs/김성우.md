## 2. 상점·강화 구현 메모 (2026-07-14)

- 구현 반영: 상점·강화 결과 코드는 명시적인 `byte` 값으로 유지하고, 화면에 표시할 문구는 `ShopMessageMapper`와 `UpgradeMessageMapper`에서 변환한다.
- 구현 반영 완료: `UpgradeController.OnDisable()`에서 선택 아이템과 결과 메시지를 초기화하며, 다른 아이템을 강화 슬롯에 올렸을 때 이전 결과 메시지를 제거한다.
- 구현 반영 완료: 강화 비용 공식의 증가 배율 `1.15`를 `upgradeCostMultiplier` 직렬화 필드로 분리했다. 공식 자체와 수치 변경 권한은 아직 팀 정책으로 확정하지 않았다.
- 구현 반영 완료: 강화 슬롯의 드롭 대상은 상위 `UpgradeSlot`의 단일 `UpgradeDropSlot`이 판정하고, 슬롯 테두리와 아이템 미리보기는 각각 별도 `Image`가 담당한다. 미리보기 이미지는 드롭 판정을 가로막지 않도록 Raycast 대상에서 제외한다.
- 팀 결정 필요: 강화 성공 판정, 비용 계산, 골드 차감 및 아이템 변경 중 어느 범위까지 서버 권한으로 둘지는 Mirror 연동 전에 결정한다.
- 현재 범위 제외: Mirror 통신 코드, 네트워크 DTO, 서버 상태 동기화, 실제 휴식맵 강화 NPC의 창 열기·닫기 연결.

## 3. 인벤토리·장비 저장 복원 구현 메모 (2026-07-14)

- 커밋 완료: `EquipmentTransaction.TryRestoreEquippedItem()`을 추가해 저장된 장비도 `EquipmentSystem`을 직접 변경하지 않고 거래 경로를 통과하도록 했다.
- 커밋 완료: `DataManager`의 `PlaceItem()`과 `EquipmentSystem.Equip()` 직접 호출을 각각 `TryPlaceItem()`과 장비 복원 Transaction 호출로 교체했다.
- 커밋 완료: 그리드 배치·UI 생성·장비 복원 실패를 확인하고, UI 생성이나 장비 복원이 실패하면 이미 변경한 상태를 되돌리도록 했다.
- 커밋 완료: `InventoryController.Instance`는 메서드 시작 시 지역 변수 `controller`에 한 번 저장하고 보조 메서드에도 전달해 같은 플레이어의 인벤토리를 끝까지 사용하도록 했다.
- 적용 이유: 지역 변수는 새 인스턴스가 아니라 동일한 객체 참조이며, 반복적인 전역 조회를 줄이고 null 검사·의존성 확인·향후 플레이어별 상태 분리를 명확하게 한다.

## 4. 인벤토리 모델·Item UI 생성 구현 메모 (2026-07-14)

- 구현 및 현재 씬 검증 완료: `InventoryGrid.RemoveItem()` 직접 변경 경로를 제거하고, 제거·배치·이동 결과는 `TryRemoveItem()`과 `TryPlaceItem()`의 실제 성공 여부를 확인하도록 통일했다.
- 구현 및 현재 씬 검증 완료: `InventoryAddResult`와 `InventoryMoveResult`는 기존 의미를 유지한 명시적 `byte` 코드로 고정하고, 인벤토리 획득 문구는 `InventoryMessageMapper`에서 변환한다.
- 구현 및 현재 씬 검증 완료: `InventoryController.TryAddItemAt()`을 일반 획득과 저장 불러오기의 공통 배치 경로로 사용하고, 성공 후 `OnItemAdded`를 한 번 발행한다.
- 구현 및 현재 씬 검증 완료: Item UI prefab 생성과 `ItemUI.Setup()` 책임은 `InventoryItemUISpawner`로 이동했다. 일반 아이템은 `OnItemAdded` 구독으로, 장착 아이템 불러오기는 `DataManager`가 같은 Spawner를 명시적으로 사용해 UI를 생성한다.
- 씬 적용 범위: 현재 `ItemUpgradescene`의 언팩된 `InventoryController` 오브젝트에만 `InventoryItemUISpawner`를 배치하고 `ItemPrefab.prefab`을 연결했다. 원본 `StatTestPrefeb.prefab` 적용 여부는 팀 회의 전까지 확정하지 않는다.
- 확인 결과: 현재 씬에서 `InventoryController`와 `InventoryItemUISpawner`가 동일 GameObject에 각각 1개 존재하고, Item UI prefab 참조가 연결되어 있다. Unity 컴파일 완료 및 Console 오류·경고 0개를 확인했다.
- 후속 확인: 일반 획득, 회전 아이템 저장·불러오기, 장착 아이템 불러오기에서 Item UI가 한 번만 생성되는지 플레이 모드로 확인한다.
- 후속 정리: `DataManager`의 Spawner 누락 경고 문구에 남아 있는 이전 명칭 `InventoryItemPresenter`를 `InventoryItemUISpawner`로 통일한다.
- 결정 상태: CAND-006의 구현 검증 단계이며 팀 승인 ADR은 아니다. Mirror 요청·응답, 서버 권한 및 네트워크 동기화 방식도 아직 결정하거나 구현하지 않았다.

- 파괴 프리팹: `Sci_Fi_Drone_D_Destructible`과 `Sci_Fi_Drone_F_Destructible` 프리팹을 만들고 각각 47개, 48개 파츠의 Artificer BuildData를 연결했다. 이동 애니메이션은 Animator Controller 없이 `CombatDroneVisualAnimator`의 절차적 동작을 사용한다.
- 공격 방향 연동: `CombatDroneArtificerDestruction`이 공격 방향 벡터와 충돌 지점을 받아 파편의 방향성 힘에 반영한다. 파괴가 시작되면 드론 Collider와 `NavMeshAgent`를 비활성화해 남은 오브젝트가 이동·충돌 판정에 개입하지 않도록 했다.
- 런타임 조절: `ArtificerRuntimeTuningTarget`이 공유 BuildData를 런타임 복제해 원본 에셋을 보존하면서 파괴 방식, 파괴 순서, 수명, 방사형·방향성 힘, 회전 속도, 중력, 바운스와 드래그를 조절한다. `ArtificerRuntimeTuningPanel`은 초심자가 바로 시험할 수 있도록 항목명을 한글화했고, 일반 몬스터용 동시 파괴를 기본으로 하되 순차 파괴도 비교할 수 있게 했다. 설정 적용 후 재생성 기능도 포함했다.
- 수동 전투 테스트: `Enemy Manual Test` 프리팹과 `EnemyManualTestReset`으로 `TestStage` 실행 시 Enemy 1·2 슬롯에 설정한 적을 4열 배치로 런타임 생성한다. 씬에 개별 적을 미리 배치할 필요가 없으며 UI 버튼 또는 `R` 키로 전체 적을 제거하고 다시 생성할 수 있다. `EnemyDestructionTarget`은 이 테스트에서만 플레이어 공격을 Artificer 파괴 요청으로 바꾸는 어댑터다.
- 추적 동작: D·F 파괴 프리팹에 기존 `EnemyFollower`와 `NavMeshAgent`를 연결했다. `Player` 태그를 기준으로 12기 모두 플레이어를 찾고 NavMesh 위에서 추적하는 것을 확인했으며, 팀원의 `EnemyFollower` 스크립트 원본은 변경하지 않았다.
- 타격 이펙트: `TestStage`에 기존 `WBH_EffectPoolManager`와 `WBH_EffectSpawner`를 사용하는 `EffectManager`를 배치하고 4개 이펙트 데이터를 등록한 뒤 Fighter의 `WBH_PlayerAnimation.effectSpawner` 참조를 연결했다. 팀원의 WBH 플레이어·이펙트 스크립트를 수정하지 않고 씬 구성만으로 풀링된 슬래시 이펙트가 재생되도록 했다.
- 바닥 충돌 원인과 수정: Artificer 파편 Raycast가 `Default` 레이어만 검사하는 반면 테스트 바닥 Collider는 `Ground` 레이어 13이어서 파편이 바닥을 통과하고 있었다. `CombatDroneArtificerDestruction`이 `StartDismantle` 직전에 Artificer와 재귀적으로 찾은 모든 `MeshElement`을 Raycast 방식, `Ground` 마스크(`8192`), `ClearDismantle`로 맞추도록 변경했으며 D·F 프리팹에도 같은 마스크를 명시했다.
- 기본 파편 값: 시연용 기본 수명 범위는 2.5~4초, 선형 드래그는 0.25, 회전 드래그는 0.2, 바운스는 0.15로 조정했다. F형 48개 파편 시험에서 파괴 직후 48개가 모두 바닥 높이 아래로 내려가지 않고 정지했으며, 수명 종료 뒤 처리 큐가 0이 되는 것을 확인했다.
- 원본·파편 전환 보강: Artificer의 `StartDismantle()`이 원본 Renderer를 즉시 숨겨 발생하던 한 프레임 깜빡임을 줄이기 위해, `CombatDroneArtificerDestruction`이 파편 렌더링 인계 시점까지 원본 Renderer를 한 프레임 유지한 뒤 끄도록 했다. Artificer 에셋 원본 스크립트는 수정하지 않았다.
- 파편 축소·디졸브: D·F 파괴 프리팹과 파괴 연출 분신 프리팹에 파편 크기 배율, 수명 후반 축소, Advanced Dissolve 기반 소멸을 적용했다. `ArtificerRuntimeTuningTarget`은 원본 로봇 재질을 직접 바꾸지 않고 인스턴스별 런타임 재질 복사본과 `Graphics.RenderMesh`용 MaterialPropertyBlock을 사용한다.
- 런타임 패널 보강: `파편 크기와 사라짐` 구역에서 파편 크기, 크기 감소 사용 여부·시작 시점, 디졸브 사용 여부·시작 시점·무늬 크기·가장자리 두께를 조절할 수 있게 했다. 순차 파괴를 선택했을 때만 전체 파괴 시간과 공격 지점·중심·바깥쪽·무작위·베이크 순서 설정이 나타나도록 구성했다.
- 스케일 곡선 수정: Artificer가 폭발 파편의 스케일 곡선을 내부적으로 `1 - fragmentProgress`, 즉 x축 `1→0` 방향으로 읽는 점을 반영했다. 기존 정방향 곡선 때문에 파편이 0 크기에서 생성되어 커졌다가 디졸브되는 것처럼 보이던 현상을 수정해, 첫 프레임부터 정상 크기를 유지하고 설정한 축소 시작 시점 이후에만 0까지 줄어들도록 했다. 런타임 검증에서 초기 파편 5개의 렌더 스케일이 모두 `1.00000`임을 확인했다.
- 풀링·실제 적 적용 문서: `Docs/Artificer_Destruction_Pooling_Guide.md`에 실제 적 본체 풀과 파괴 연출 풀을 분리하는 구조, 공격 방향 전달, BuildData 런타임 복제, Ground 충돌 설정 전파, Raycast·Simple 방식 선택, 재사용 초기화 순서와 성능 점검 기준을 정리했다. 실제 적은 테스트용 `EnemyDestructionTarget`이나 `EnemyManualTestReset`에 의존하지 않고 정식 체력·사망 처리에서 파괴 연출 풀을 호출하도록 한다.
- 설계 문서 PDF: `Artificer_Destruction_Pooling_Guide.md`에 역방향 스케일 곡선 주의사항을 보강하고, `Docs/파란색 및 회색 깔끔한 및 단순한 인포그래픽.pdf`의 크림·청회색 카드형 디자인을 참고해 SUIT 글꼴 기반 A4 9쪽 PDF를 `Docs/Artificer_Destruction_Pooling_Guide.pdf`로 제작했다. 표지, 목차, 입력→연출→풀 반환 흐름도, 표·코드 블록과 페이지 번호를 포함하고 전체 페이지를 PNG로 렌더링해 잘림·겹침·한글 표시를 확인했다.
- Enemy 로봇 전수 분류: `Assets/Resources_GoogleDrive/Props/Enemy`의 프리팹 72개를 Unity에서 점검해 로봇 본체 44개와 비로봇 28개를 구분했다. 현재 안전 생성기는 로봇 이름이나 에셋 묶음별 예외 절차 없이 Renderer 구성을 자동 판별한다. 정적 메시 로봇은 읽기 가능한 메시 복사본을 만들고, 스킨드·혼합 로봇은 현재 자세를 Bake해 보이는 Renderer를 정적 파괴 연출 프리팹에 모은다.
- 안전 파괴 연출 생성기·빠른 적용 문서: 최상단 `SW > Artificer` 메뉴에 `일반 적 파괴 연출 프리팹 생성 (동시)`과 `보스 파괴 연출 프리팹 생성 (순차)`를 제공한다. 선택한 원본을 수정하지 않고 각자 팀원 폴더에 파괴 연출 프리팹, Renderer별 정적 메시, 전용 BuildData를 만들며 루트에 `Artificer`, `CombatDroneArtificerDestruction`, `ArtificerFragmentBurstProfile`, `ArtificerRuntimeTuningTarget`, `EnemyDestructionVisual`을 자동 추가·연결한다. 보스 모드는 생성된 BuildData의 MeshElement가 2개 이상인지 검증하고 1개면 결과물을 정리한 뒤 파츠 분리가 필요하다는 오류를 표시한다. 단일 Cube는 보스 모드에서 안전하게 거부된다. 자동 생성된 일반 적 프리팹을 런타임 재생해 파괴 시작 시 `active=True`, `playing=True`, 완료 후 `active=False`, `playing=False`, `IsDismantled=True`와 Console 오류 0개를 확인했다. 이 절차와 `Enemy Manual Test`의 Enemy 1·2 슬롯 연결법을 Markdown·SUIT PDF에 반영했다.
- 일반 적·보스 분할 최적화 분리: 일반 몬스터는 애니메이션 메시를 정적 파괴 연출로 바꾸는 과정에서 이미 메시 수가 충분히 줄어들고 기존 연출 품질·성능 문제가 적으므로 `SplitMode.Elements`와 `Use Position=true`를 유지해 연결된 메시 파츠를 세밀하게 분리한다. 파츠 수가 매우 많은 보스만 `SplitMode.Materials`와 `Use Position=false`를 사용해 Renderer·머티리얼 단위의 큰 그룹으로 묶는다. 임시 BuildData 검증에서 `SciFiDroid01Animated` 일반형은 기존과 같은 34개 MeshElement, `Sci-Fi ToiletMech Skin 1` 보스형은 기존 세밀 분할 742개 대신 25개 그룹으로 생성됐고 변환 스크립트 진단 오류는 0개였다. 이 설정은 이미 저장된 BuildData를 자동 변경하지 않으므로 기존 일반 몬스터는 재생성할 필요가 없고, 기존 보스 파괴 연출만 보스 메뉴로 다시 생성한 뒤 리셋 매니저 또는 파괴 연출 풀의 참조를 새 프리팹으로 교체해야 한다.
- 혼합 파괴 조절 패널: `ArtificerRuntimeTuningPanel`의 기본 적용 범위를 `일반/보스 구분 유지 (추천)`로 바꿨다. 안전 생성 프리팹이 가진 최초 파괴 방식을 `ArtificerRuntimeTuningTarget`이 런타임에 보존해 일반 적은 동시, 보스는 순차 파괴를 유지하며 수명·크기·디졸브·힘·움직임만 공통 조절한다. 비교용 `전체 동시 파괴`, `전체 순차 파괴`도 제공하고, 추천 모드의 순차 세부 설정은 보스에만 적용한다. 일반 프리팹과 보스 프리팹을 함께 활성화한 검증에서 추천 모드는 `Simultaneous/Sequential`, 전체 동시 모드는 `Simultaneous/Simultaneous`로 적용됨을 확인했다.
- 파편 속도 곡선: Artificer 원본을 수정하지 않고 `CustomDismantle` 확장을 사용하는 `ArtificerFragmentBurstProfile`을 추가했다. `Explode` 파편별 `BuildQueue`를 독립 추적하고, 파편 수명의 빠른 구간에서는 3차 Ease Out으로 초기 배수에서 1배까지 빠르게 낮춘 뒤 남은 구간에서는 Smoothstep으로 마지막 배수까지 감속한다. 매 프레임 새 배수와 이전 배수의 비율만 속도에 반영해 기존 중력·드래그 계산을 보존하며, 선형 드래그를 포함한 자유 비행 거리 적분으로 커브 미사용 시의 이동 거리에 가깝게 자동 정규화할 수 있다. 안전 생성기는 새 프리팹에 이 컴포넌트를 자동 추가하고 Artificer의 `Custom Dismantle`에 연결하며, 기존 SW 파괴 연출 프리팹 7개도 같은 구조로 갱신했다. 기존 전용 BuildData가 존재하는 D·F 및 안전 생성 결과 4개는 비어 있던 프리팹 참조를 다시 연결했고, 전용 데이터가 없던 `SciFiDroid01Animated_DestructionVisual`에는 34개 MeshElement BuildData를 새로 생성해 연결했다. 최종적으로 7개 모두 필수 다섯 컴포넌트·BuildData·Custom Dismantle 연결 검증을 통과했다.
- 속도 커브 한글 패널: `6. 처음에 팍 튀는 속도` 구역에 커브 사용 여부, 처음 속도 배수, 빠르게 튀는 수명 비율, 마지막 속도 배수, 바닥에서 띄우는 비율, 기존 이동 거리 자동 보정을 배치했다. `원래 움직임`은 커브·바닥 이탈 보정을 끄고 `1.0 / 0.10 / 1.0 / 0`, `강한 타격`은 `3.5 / 0.10 / 0.12 / 0.35`, `묵직한 보스`는 `2.3 / 0.18 / 0.06 / 0.25`를 사용하며 두 연출 프리셋은 거리 자동 보정을 켠다. 패널 값을 바꾼 뒤 활성 연출만 갱신할 때는 `현재 값 적용`, 풀과 실제 적을 처음 상태부터 다시 시험할 때는 `적 전체 다시 생성 + 적용`을 사용한다.
- 첫 사용 일관성 보강: Artificer의 첫 `Start()`가 Awake·풀 준비 단계에서 적용한 MeshElement 운동 설정을 프리팹 기본값으로 다시 만들 수 있는 경우를 확인했다. 실제 파괴 직전 `PrepareForDismantle`에서 현재 런타임 값을 다시 적용하도록 보강해 첫 사용과 풀 재사용이 모두 `Explode` 운동 및 동일한 속도 곡선으로 시작하도록 했다.
- 속도 곡선 검증: 전용 BuildData가 연결된 `Sci_Fi_Drone_D_DestructionEffect` 3개를 실제 `EnemyDestructionVisual.Play(...)` 첫 사용 경로로 동시에 파괴해 각 47개, 총 141개 파편이 독립적으로 추적되는 것을 확인했다. 세 인스턴스 모두 `Custom Dismantle` 연결, `Explode` 큐 47개, 초반 고속에서 후반 저속으로 감소하는 배율을 확인했고 Console 오류와 경고는 0개였다. 별도 수치 검증에서는 수명 2초·선형 드래그 0.12 조건에서 거리 보정 비율이 `0.999`였다.
- 속도 곡선 정지 문제 수정: Artificer는 `CustomDismantle`이 연결되면 기본 `RemoveElement(...)` 대신 사용자 `Remove(...)`만 호출한다. 초기 구현이 속도만 조절하고 위치 적분을 넘기지 않아 파편이 전혀 이동하지 않는 원인이 됐다. `ArtificerFragmentBurstProfile.Remove(...)`에서 Artificer의 기본 이동·중력·회전·충돌 계산을 다시 호출하고, 사용자 경로의 추가 행렬 변환은 상쇄하도록 수정했다. 런타임 복제 BuildData에 `mesh`만 있고 렌더 캐시 `rp`가 없는 경우도 파괴 직전에 해당 불완전 캐시만 비워 Artificer가 두 값을 함께 재생성하도록 보강했다.

## 14. 장착 아이템 메인 스탯 비교 툴팁 구현 메모 (2026-07-27)

- 비교 규칙: `EquipSlotRules.TryGetEquipSlot`과 `TryGetComparisonSlot`을 추가해 무기는 무기, 방어구는 Helmet·Chest·Boots의 동일 슬롯만 비교하도록 했다. 포션·유물과 동일 아이템 자체는 기존 단일 툴팁을 유지한다.

- UI 분리: 기존 `TooltipManager`의 텍스트·색상·자동 높이 책임을 재사용 가능한 `TooltipUI`로 옮기고, Manager는 표시 대상 결정·마우스 위치·Canvas 경계 보정·비교 패널 생명주기만 담당하도록 정리했다.

- 현재 검증 상태: 정적 코드 기준으로 비교 계산·Resolver·표시 분리와 `CS0165` 미할당 지역 변수 수정 반영을 확인했다. Unity 컴파일, Inspector 참조, 무기·헬멧·상의·부츠 비교 및 화면 가장자리 Play Mode 검증은 후속 확인이 필요하다.

- 구현 목적: 인벤토리에 소지한 유물이 장착 과정 없이 플레이어 최종 스탯에 반영될 수 있도록 기본 연결 구조를 마련했다. 유물 원본 데이터나 인벤토리 상태를 별도로 복제하지 않고 `InventoryController`가 소유한 현재 아이템을 기준으로 계산한다.
- 역할 경계: `PlayerRelicEffectProvider`는 `IStatSetProvider` 구현체이며 인벤토리 안의 `ItemCategory.Relic`만 찾아 `StatSet`으로 변환한다. 인벤토리 아이템을 추가·삭제하거나 `PlayerStatManager`의 내부 상태를 직접 수정하지 않고, 현재 유물 효과를 읽어서 제공하는 어댑터 역할만 담당한다.
- 현재 계산 범위: 유물 `ItemInstance`의 강화 적용 메인 옵션과 굴려진 보조 옵션을 기존 `StatSetMapper`로 합산한다. 유물 고유 효과, 조건부 효과, 전투 중 발동 효과는 아직 이 계산에 포함하지 않았으며 향후 효과 정책이 확정되면 별도 처리가 필요하다.
- 스탯 연결: `PlayerStatManager`의 `relicProviderBehaviour`에 제공자를 연결하고 `Recalculate()`에서 장비·버프와 마찬가지로 `IStatSetProvider.GetStatSet()`을 호출한다. 현재 `PlayerStat` 계산 인자 구조를 유지하기 위해 유물 수치는 버프 수치와 더한 뒤 기존 버프 계층 인자로 전달하며, 이 방식은 스탯 계층 개편 시 이우진 팀원과 다시 확인할 수 있는 현재 구현이다.
- 갱신 시점: 현재는 인벤토리의 `OnItemAdded` 이벤트와 제공자의 `Start()`에서 재계산한다. 유물 판매·삭제·월드 드랍처럼 인벤토리에서 빠지는 흐름은 제거 이벤트가 정리된 뒤 같은 제공자에 연결해야 하며, 아직 자동 갱신이 완성됐다고 보지 않는다.
- 초기화 순서 안전 처리: `PlayerStatManager.Awake()`가 `InventoryGrid.Awake()`보다 먼저 실행돼도 빈 유물 목록으로 계산을 계속할 수 있도록 `InventoryGrid.GetAllItems()`가 초기화 전에는 빈 결과를 반환하게 했다. 실제 아이템이 들어오면 추가 이벤트와 `Start()` 재계산으로 최신 상태를 다시 반영한다.
- WJ 씬 연결: `Assets/WJ_TestPlace/Scene/WJ_StatSystemTestScene.unity`의 `PlayerStatManager` 오브젝트와 `Assets/WJ_TestPlace/Scene/WJ_Act1_DropTest.unity`의 실제 `Fighter` 오브젝트에 각각 `PlayerRelicEffectProvider`를 추가했다. 각 제공자는 해당 씬의 `InventoryController`와 `PlayerStatManager`를 직접 참조하므로 별도 Singleton은 추가하지 않았다.
- 함께 이관한 참조: 두 WJ 씬의 기존 아이템 툴팁 UI를 현재 `TooltipUI`와 `TooltipManager` 구조로 옮기고 `EquipmentSystem`과 기본 툴팁 View를 연결했다. 씬만 따로 반영하면 Missing Script가 생길 수 있으므로 `PlayerRelicEffectProvider.cs/.meta`, `PlayerStatManager`, `TooltipUI`, `TooltipManager` 관련 변경을 같은 머지 범위로 취급한다.
- 검증 결과: 두 WJ 씬 모두 Unity 컴파일 후 Play Mode에서 새 오류·경고가 없었고, 씬 검사에서 Missing Script와 깨진 Prefab이 각각 0개였다. 실제 유물별 수치·고유 효과와 저장 후 재접속 흐름은 유물 데이터와 정책이 확정된 뒤 추가 검증해야 한다.
- 현재 범위 제외: Mirror 동기화, 서버 권한 판정, 유물 고유 효과 실행, 중복 유물 규칙, 판매·드랍 제거 이벤트 정책은 이번 기본 구조에서 확정하지 않았다.
