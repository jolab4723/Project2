## 2. Project2에 맞춘 핵심 결정

### 2.1 효과의 목표

- 무기는 공격 행동과 표적 선택을 바꾼다.
- 투구는 표적·행동 순서·자원 판단을 바꾼다.
- 상의는 피해를 버티는 방식과 반응 시간을 바꾼다.
- 부츠는 이동 리듬·재배치·탈출 판단을 바꾼다.
- 유물은 가방 칸을 점유하는 동안 빌드 규칙을 바꾼다.
- 한 아이템은 한 가지 상황에서 분명히 강하고, 다른 이득이나 공간·조건·시간 중 하나를 포기하게 한다.

### 2.2 빌드의 계산 단위

Fighter 무기 두 개나 Gunner 무기 두 개를 한 플레이어의 동시 빌드로 계산하지 않는다. 빌드는 다음 단위로 기록한다.

`핵심 무기 1개 + 실제 동시 장착 가능한 방어구/소지 유물 + 기존 스킬 + 선택적 팀원 상호작용`

각 빌드는 핵심 행동, 강한 상황, 약한 상황, 대체 가능한 Rare/기본 아이템을 함께 적는다.

### 2.3 현재 P2 전투 경계의 사용 범위

- 현 동기 후속 피해 큐는 연쇄 번개와 동일 대상 화염 추가타처럼 **즉시 해결되는 공격형 효과**에 사용한다.
- 현 스냅샷은 **직접 피해 처리 진입 시점**의 공격력·치명타·관통·속성 보너스를 해당 동기 큐까지 고정한다.
- P3-A에서 투사체에 발사 무기 인스턴스와 장착 세대를 보존하는 최소 계약을 추가했다. 피해 수치는 기존 정책대로 명중 시점 Stat을 읽으며, Burn 틱·지연 폭발·메아리 재생은 여전히 별도 계약이 필요하다.
- 현 후속 중복 키 `(AttackId, DamageCause, Target)`는 단일 장착 무기의 동기 공격형 효과까지만 보장한다. 같은 공격에 여러 효과 생산자를 허용하는 시점에만 효과 ID 또는 실행 인스턴스를 키에 추가한다.

## 4. 단계별 실행 계획

### P2-B — 인페르노 근접 기본 공격 화염 추가타

2026-09-16에 `item.weapon.axe.inferno`를 대상으로 1인 구현과 자동 검증을 완료했다. 아래 착수 게이트는 실제 적용 결과를 반영해 보존한다.

#### 착수 게이트

1. 최종 대상 아이템을 실제 ItemTable의 인페르노 `itemId`로 확정한다.
2. `DamageCause.Direct`만으로 분류하지 않고, Fighter 권한 공격이 실제로 처리 중인 직접 대상 집합을 동등한 분류 경계로 재사용했다. 이번 효과 하나를 위해 새 `AttackKind`는 추가하지 않았다.
3. 이 분류를 위해 다른 담당자 스크립트를 수정해야 하면 파일과 이유를 먼저 밝히고 사용자에게 `이 스크립트를 수정할까요?`라고 승인받는다.
4. 아이템 연결의 원본은 ItemTable의 인페르노 행으로 확정했다. 신규 실행 타입 SO는 P2-A와 마찬가지로 EffectPool에 수동 생성한 시범 자산이므로, 양산 전에 WJ 데이터 모델·임포터 수정 승인을 받아 Table→JSON→SO 재생성에 안전하게 편입한다.

#### 구현 범위

- 근접 기본 직접 공격이 실제 살아 있는 대상에게 적중한 뒤 같은 대상에 공격력 20% 화염 Effect 피해 1회.
- 직접 공격 처리 진입 스냅샷 사용.
- 후속 피해는 비치명, 재귀 발동 금지, 같은 공격·대상에서 중복 금지.
- 스킬, 총기, 산탄 펠릿의 잘못된 합산, 기존 Effect, DoT에서는 발동하지 않는다.
- 직접타로 대상이 죽으면 후속타는 실행하지 않는다.
- 효과타가 처치하면 기존 P1 처치 귀속을 한 번만 사용한다.
- 이 항목은 최초 P2-B 구현 범위였다. 이후 Round05 보완에서 속성 직접타의 기존 상태이상 매핑과 인페르노 연출·정식 Burn 실측이 별도 변경으로 추가됐다. 지연 실행과 범용 실행기 팩토리는 만들지 않았다.

#### 완료 기준

- 직접 100 + 화염 20의 순서와 합계.
- 같은 대상 Direct + Effect 허용, 두 번째 Effect 거절.
- 치명 직접타와 비치명 화염 추가타 대조.
- 스킬·총기·Effect·DoT 미발동.
- 직접 처치 시 미발동, 효과 처치 시 보상 1회.
- P1 76/76 및 P2-A 39/39 회귀.
- 1인 검증 완료 후 원격·4인 범위는 별도 표기한다.

#### 완료 기록

- 인페르노 근접 기본 직접타가 살아 있는 실제 대상에 적중했을 때만, 같은 공격 번호와 공격 시작 스냅샷을 사용해 공격력 20%의 비치명 Fire `Effect` 피해를 한 번 등록한다.
- 같은 적의 다중 Collider는 Direct 1회와 Effect 1회로 끝나며, 스킬·기존 Effect·DoT·권한 공격 밖의 임의 Direct에서는 발동하지 않는다.
- 직접타 처치에는 추가타가 생기지 않고, 추가타 처치는 기존 P1 처치 보상 경로를 정확히 한 번 사용한다.
- 최초 P2-B 구현에서는 새 범용 실행기·Factory·스케줄러·Burn·VFX를 추가하지 않았다. 이후 Round05 보완에서 기존 상태이상 체계를 통한 Burn과 전용 피격 표현만 추가했고, 실행 책임은 계속 `ItemTriggerManager_MirrorTest`의 좁은 자격 검사와 기존 동기 후속 피해 큐에 유지했다.
- 실제 생성 데이터와 SW Fighter/적 프리팹 기반 P2-B 29/29, P2-A 39/39, P1 76/76이 통과했고 검증 직후 Console Error는 0건이었다.
- 원격 클라이언트 화면, 4인 MPPM, 정식 Act1 체감·성능은 검증하지 않았다. 상세 내용은 `UniqueEffect_P2B_Inferno_Handover.md`를 따른다.

### P3-A — 실제 Gunner 공격형 효과 1종

2026-09-17에 `item.weapon.rifle.glassrail`(유리빛 궤도)을 첫 실제 Gunner 대상으로 연결했다.

- 공격 단위는 **서버가 생성한 Rifle 투사체 한 발**이다. 투사체의 직접타가 유효하고 발사한 정확한 `ItemInstance.instanceId`와 장착 세대가 명중 순간까지 유지될 때만 같은 대상에 공격력 15%의 비치명 Ice `Effect` 피해를 한 번 등록한다.
- 피해 수치는 발사 순간에 고정하지 않고 기존 Gunner 정책대로 직접타 처리 진입 시점의 Stat 스냅샷을 후속타까지 사용한다. 투사체에는 효과 판정에 필요한 아이템 ID·인스턴스 ID·장착 세대·효과 SO만 보존한다.
- 다른 무기, 같은 `itemId`의 다른 인스턴스, 같은 인스턴스의 해제 후 재장착은 이전 탄의 고유효과만 취소한다. 이전 탄의 직접 피해는 그대로 처리한다.
- 공격 출처는 투사체 직접 피해 호출의 동기 범위에서만 공개하며, 영구 공격 캐시·범용 실행기·Factory·스케줄러를 추가하지 않았다.
- 동일 적의 명시적 다중 Collider, 무기 교체, 동일 정의 다른 인스턴스, 해제·재장착, 두 탄의 역순 도착과 비치명·냉기·15% 스냅샷을 18/18 검사로 확인했다.
- 직접 Ice 타격에는 Round05의 기존 매핑으로 `Freeze1`이 적용된다. 추가타는 상태이상을 `null`로 전달해 한 탄에서 Freeze를 두 번 갱신하지 않는다.
- 15%는 첫 튜닝값이며 최종 밸런스 확정값이 아니다. 실제 입력·AnimationEvent·Network Spawn·물리 충돌을 잇는 solo Host 플레이와 원격/4인 검증은 아직 완료로 기록하지 않는다.
- 상세 인계는 `UniqueEffect_P3A_GlassRail_Handover.md`를 따른다.

### P3-B — 방어구·유물 기존형 대표와 활성 어댑터

먼저 기존 사건으로 표현할 수 있는 세 종류를 검증한다.

1. H3 저마나 회복형: 기존 Threshold 경계와 자원 0·경계값을 검증한다.
2. B1 회피 사용 이동형: 현 `OnDodge`가 성공 회피가 아니라 회피 상태 진입임을 툴팁과 테스트에 명시한다.
3. R2 협동 오라형: 소지 중 활성, 동일 효과 비중첩, 가방 이동·회전·드래그 취소의 소유권 유지, 실제 거래·드랍 시 비활성화를 검증한다.

이 단계에서 `PlayerRelicEffectProvider`를 방어구까지 억지로 확장하지 않는다. 실제 장착 슬롯 변화에서 방어구 효과를 활성·해제하는 작은 어댑터를 별도 책임으로 둔다. 다른 담당자 영역 수정이 필요하면 사전 승인을 받는다.

### P4-A — 상태이상 계약

Burn이나 냉각을 사용하는 첫 효과 전에 다음을 확정한다.

- 상태 출처 플레이어와 공격 번호.
- 최초 적용과 갱신 시 틱 시점.
- 지속시간 갱신·중첩·세기 갱신 규칙.
- 적 풀 반환·재사용 시 정리.
- 상태 피해 처치 귀속과 Effect 재발동 차단.
- 보스 저항과 면역 표시.

초기 순서는 냉각 또는 단순 Burn 1종 → 재적용 → 풀 재사용 → 보스 저항이다. 모든 상태이상을 한 번에 일반화하지 않는다.

### P4-B — 실제 완성 빌드 대표 검증

- Fighter 전기 확산 빌드 1개.
- Fighter 화염 근접 빌드 1개.
- 실제 Gunner 중심 빌드 1개.
- 방어구·유물 기존형을 포함하되 실제 슬롯에서 동시에 쓸 수 있는 조합만 기록한다.
- 협동 회복을 거절해야만 유지되는 저체력 빌드는 대표 성공 사례로 채택하지 않는다.

### P5-A — 피격 결과와 보호막 계약

상의 C2 태양전지 보호막을 첫 신규 방어 시스템 후보로 삼되, 구현 전에 피해 처리 결과가 다음을 구분하도록 한다.

- 공격자와 실제 HP 손실량.
- 무적·회피·보호막 흡수·HP 피해·사망.
- 마지막 유효 피해 시각.
- 보호막 최대치, 비중첩·갱신, 흡수 순서, 해제·사망·새 런 수명.
- 서버 권한과 원격 표시.

C2 출발 규칙은 `HP 80% 이상 + 8초간 유효 피해 없음 → 최대 HP 15% 비중첩 보호막` 후보로만 둔다. 수치는 실제 전투 검증 뒤 확정한다.

### P5-B — 다음 공격 토큰

- 회피 사용, 피격, 스킬 사용 중 하나의 사건만 생산자로 선택한다.
- 소비 대상은 `다음 유효 기본 공격 1회`처럼 명확히 한다.
- 빗나감·무적·다중 Collider·다중 펠릿·무기 교체·사망·새 런에서 토큰 수명을 검증한다.
- 보호막과 다음 공격 토큰은 서로 다른 작은 단계로 구현한다.

### P6 — 시간·영역·복합 효과

첫 지연 효과가 확정되기 전에는 범용 스케줄러를 만들지 않는다. 구현 순서는 다음과 같다.

1. 정적 영역 1종.
2. 단순 지연 폭발 1종.
3. 관통 또는 끌어당김 1종.
4. 제한된 메아리·재생 1종.

필요해지는 시점에만 예약 실행의 소유 플레이어, 원본 아이템/무기 세대, 취소 조건, 최대 예약 수, 적 풀 재사용 안전성을 갖춘 제한된 스케줄러를 만든다. 현 동기 후속 큐를 시간 지연 용도로 사용하지 않는다.

## 5. 데이터 양산 규칙

- 효과 ID, 한국어 설명, 표시 계수와 실행 필드는 같은 원본에서 재생성되어야 한다.
- importer가 모르는 타입을 조용히 무시해서는 안 된다. 실패 또는 명시적 수동 예외로 드러나야 한다.
- P2-A의 `UE_ArcBladeChainLightning` 수동 SO는 시범 예외다. 재수입으로 삭제·연결 손실이 없는지 양산 전 다시 확인한다.
- 효과를 찍어낼 때는 `아이템 행 → 효과 행/타입 → 생성 SO → ItemDefinitionSO 참조 → 실제 장착 → 서버 실행 → 한국어 툴팁`을 한 묶음으로 검증한다.
- 런타임 스택은 영구 아이템 스택, 전투 중 임시 열·토큰·보호막을 분리한다.
- 동일 효과 사본은 기본적으로 능력과 발동 횟수를 합산하지 않는다. 예외가 필요한 효과만 명시한다.

## 6. 최적화 원칙

- 현재 아크 블레이드 최대 조건의 이론적 호출량만으로 `NonAlloc`, 풀, 공간 분할을 선행 도입하지 않는다.
- 4인 실제 전투에서 서버 프레임 시간, 효과 발동 수, 성공 구간 RPC 수, GC 할당, LineRenderer 동시 수를 먼저 측정한다.
- 성공 구간 RPC가 실제 병목이면 한 공격의 구간을 묶어 전송하는 방식을 먼저 검토한다.
- 화면 표현 풀링은 반복 생성이 Profiler에서 확인될 때 도입한다.
- 최적화로 서버 판정, 대상 상한, 벽 차단, 수명 정리를 약화시키지 않는다.

## 7. 공통 검증표

각 신규 효과에서 관련 항목만 선택하되, 선택하지 않은 이유를 남긴다.

- 서버 단독 판정과 원격 표시 분리.
- 직접·스킬·Effect·DoT 분류.
- 공격당·대상당·효과당 중복.
- 다중 Collider, 다중 직접 대상, 산탄·자동 사격.
- 치명타 허용 여부와 공격 스냅샷 시점.
- 무적·보호막·실제 HP 손실·사망 결과.
- 처치·경험치·드랍 귀속 1회.
- 장착·해제·드랍·거래·사망·새 런·재접속 수명.
- 적 풀 반환·재사용.
- 데이터 재수입 후 참조와 한국어 툴팁.
- 1인, Host, 원격 Client, 4인 중 실제로 검증한 범위를 구분.
- P1 Foundation과 이미 완료된 대표 효과 회귀.

## 8. 작업 중지·승인 지점

- 다음 단계의 실제 구현은 사용자의 진행 지시와 해당 단계의 데이터·담당 경계를 확인한 뒤 시작한다.
- 다른 담당자 우선 영역의 스크립트는 대상 파일과 이유를 밝히고 명시적 승인을 받은 뒤 수정한다.
- Scene, Prefab, ProjectSettings, Packages 변경은 필요성과 영향 범위를 먼저 알린다.
- 효과 수치와 18종 세부안은 구현 승인으로 간주하지 않는다.
- 원격·4인 검증이 패키지나 에디터 문제로 막히면 1인 통과를 다인 완료로 확대 표현하지 않는다.

## 9. 다음 시작점

다음 진행 시에는 P3-A의 실제 solo Host 입력·투사체 Spawn·충돌을 먼저 확인하고, 필요하면 Host+원격 Client와 4인 MPPM으로 확대한다. 그 뒤 P3-B의 H3/B1/R2 중 실제 데이터와 현재 사건 경계가 가장 명확한 하나만 선택한다. 방어구 활성 어댑터나 다른 담당자 스크립트가 필요하면 수정 전에 대상과 이유를 밝히고 승인을 받는다.
