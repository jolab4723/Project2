## 3. 버그 수정 항목

### BUG-01. 멀티 인벤토리가 구형 디자인으로 표시됨

#### 사용자 관찰

멀티플레이에서 인벤토리가 최신 디자인이 아닌 구형 디자인으로 나타난다.

#### 코드·기록 근거

`MirrorLocalPlayerUIBinder`는 지정된 `InventoryView`와 `InventoryPartView`를 현재 로컬 플레이어의 인벤토리 상태에 연결한다. 따라서 인벤토리 동작 코드를 공유하더라도, 실제 연결된 UI 자산이 최신 디자인인지 여부는 별도 확인이 필요하다. [S3]

과거 통합 검증 문서에는 멀티 UI에 오래된 사본이 들어간 문제가 기록돼 있다. 다만 이후 공용 씬 통합이 진행됐으므로, 과거 문제가 현재 인벤토리 증상의 원인이라고 단정하지 않는다. [S1][S2]

#### 점검·수정 방향

1. 문제가 나타난 씬에서 실제로 활성화되는 인벤토리와 바인더 참조를 확인한다.
2. 싱글과 멀티에서 연결된 프리팹, 씬별 덮어쓰기, 하위 UI 구성을 비교한다.
3. 최신 디자인을 적용하되, 로컬 플레이어 소유 연결과 기존 인벤토리 기능을 유지한다.
4. 동기화 로직을 새로 만드는 대신 화면 자산·참조 차이를 먼저 해소한다.

#### 완료 기준

- [ ] 싱글과 멀티가 의도한 동일한 최신 인벤토리 디자인을 사용한다.
- [ ] 네 클라이언트가 각자 자신의 아이템과 장비를 표시한다.
- [ ] 아이템 이동·장착·해제 및 캠프 상점·강화 연결이 유지된다.
- [ ] 씬 이동, 캠프 재방문, 재접속 후 구형 화면이나 다른 플레이어의 데이터로 바뀌지 않는다.

### BUG-02. 설정창·단축키 안내·미니맵의 표시 순서가 잘못됨

#### 사용자 관찰

- 설정창을 열어도 게임 단축키 안내가 위에 남아 확인 버튼 등을 가린다.
- 인벤토리를 열어도 미니맵이 위에 표시돼 인벤토리를 가린다.

#### 코드·기록 근거

`KY_PopupManager.Show()`는 `SetAsLastSibling()`으로 팝업을 같은 부모의 마지막 자식으로 이동시킨다. `SetBackgroundInput()`은 대상 `CanvasGroup`의 `interactable`과 `blocksRaycasts`를 변경하지만, 화면을 숨기거나 Canvas의 정렬 값을 바꾸지는 않는다. [S4]

**별도 Canvas·정렬 설정과 화면 계층의 불일치가 원인 후보**다. 현재 어떤 Canvas의 값 때문에 문제가 발생하는지는 실제 씬과 실행 화면으로 확정해야 한다.

#### 점검·수정 방향

화면 우선순위를 다음 원칙으로 정리한다. 숫자는 기존 프로젝트의 정렬 규칙을 조사한 뒤 결정하며, 임의의 큰 값으로 덮지 않는다.

```text
HUD·미니맵
    < 인벤토리 등 일반 창
    < 설정창
    < 확인창·키 재설정 안내창
```

1. 문제가 발생한 창들의 부모 계층, Canvas, `sortingOrder`, `overrideSorting`을 함께 확인한다.
2. 설정창 뒤 게임 단축키 안내는 숨기거나 설정창 아래로 배치한다. 설정창 자체의 키 설정 UI와 구분한다.
3. 인벤토리가 표시될 때 미니맵이 그 위를 가리지 않도록 정렬한다.
4. 화면 정렬과 별개로, 뒤쪽 UI가 앞쪽 버튼의 클릭을 가로채는지도 검사한다.
5. 팝업을 닫으면 기존 HUD 표시와 입력 상태가 정상 복원되도록 한다.

#### 완료 기준

- [ ] 설정창의 적용·확인·취소 버튼이 가려지지 않고 실제로 클릭된다.
- [ ] 인벤토리 위에 미니맵이나 게임 단축키 안내가 겹치지 않는다.
- [ ] 키 재설정 안내와 확인 대화상자는 의도한 최상단에 표시된다.
- [ ] ESC로 열기·닫기를 반복해도 정렬과 입력 차단이 꼬이지 않는다.
- [ ] FHD와 실제 사용 중인 고해상도 환경에서 같은 기준을 만족한다.

### BUG-03. Act1 보스 인트로에서 플레이어 4명이 보이지 않음

#### 사용자 관찰

Act1 보스 인트로에서 플레이어 4명이 밀려나는 모습을 보여야 하지만, 플레이어가 보이지 않는다.

#### 코드·기록 근거

`MirrorBossIntro`는 실제 네트워크 플레이어의 Renderer를 숨기고, 별도의 연출용 외형 대역을 만든다. 첫 대역을 플레이어 타임라인 트랙에 연결하고, 다른 대역에는 첫 대역의 뼈대 변환을 복사하는 구조다. 실제 플레이어를 숨기는 처리 자체는 의도된 동작이다. [S5]

실행 기록에는 Act1 대역 4개, 공통 시각, 카메라 연결, 종료 복원이 확인됐다고 적혀 있다. 그러나 **대역의 생성·연결 확인만으로 네 명이 화면에 보이며 자연스럽게 밀려나는 연출까지 통과했다고 판단하지 않는다.** 사용자 관찰과 기록이 다르므로 동일 빌드·씬·설정에서 화면을 다시 대조한다. [S1]

#### 점검·수정 방향

1. 각 클라이언트에서 대역 개수뿐 아니라 실제 렌더링 상태와 화면 노출 여부를 확인한다.
2. 대역의 위치·배율, 타임라인 원점, 슬롯 간격, 카메라 위치·표시 대상을 대조한다.
3. Fighter/Gunner 혼합 구성에서도 애니메이션이 올바르게 적용되는지 확인한다.
4. 네 명이 밀려나는 이동과 카메라 구도를 기존 싱글 연출의 의도에 맞춘다.
5. 종료·중단·씬 이탈 시 실제 플레이어 표시와 입력이 복원되는지 확인한다.

#### 완료 기준

- [ ] 네 클라이언트 화면 모두에서 네 명의 대역이 식별된다.
- [ ] 네 명이 의도한 위치에서 자연스럽게 밀려난다.
- [ ] 실제 플레이어와 대역이 중복 표시되지 않는다.
- [ ] 종료 후 대역은 제거되고 실제 플레이어·HUD·입력이 복원된다.
- [ ] 재접속이나 씬 전환으로 캐릭터가 영구적으로 숨겨지지 않는다.

### BUG-04. Act2 보스 인트로 연결 누락과 잡아채는 연출 개선

#### 사용자 관찰

Act2 보스가 손으로 플레이어를 채가는 느낌이 자연스럽지 않다. 멀티 보스 인트로에서 플레이어가 보이지 않는 문제도 함께 확인해야 한다.

#### 코드·기록 근거

최신 실행 기록에는 Act2의 `NetworkEnemyWaveSpawner.bossIntro`가 `null`이라 인트로를 건너뛰고 보스를 생성한 문제가 남아 있다. `ServerTryStartSession()`도 보스 세션이면서 `bossIntro != null`일 때만 인트로 시작을 요청한다. [S1][S6]

이 연결 누락과 연출의 부자연스러움은 별도 항목으로 관리한다. 연결 누락이 모든 플레이어 비표시 증상의 공통 원인이라고 단정하지 않는다.

#### 점검·수정 방향

**1단계 — 인트로 재생 복구**

- 실제 Act2 보스 씬의 스포너와 `MirrorBossIntro` 참조를 확인한다.
- 서버가 시작·종료를 결정하고 네 클라이언트가 같은 인트로를 재생하는지 확인한다.
- 인트로 종료 전 실제 전투 보스가 잘못 생성되거나 전투가 시작되지 않는지 확인한다.

**2단계 — 손으로 잡아채는 동작 보정**

- 보스 손이 플레이어에게 닿는 시점과 플레이어 이동 시작 시점을 맞춘다.
- 손과 플레이어가 떨어져 보이거나 갑자기 순간이동하는 구간을 수정한다.
- 기존 타임라인을 우선 활용하고, 4인 배치·카메라 구도를 함께 조정한다.

#### 완료 기준

- [ ] Act2 인트로 필수 참조가 정상 연결된다.
- [ ] 네 클라이언트에서 인트로가 생략되지 않고 플레이어가 보인다.
- [ ] 손의 접촉 위치·시점과 플레이어 이동이 자연스럽게 이어진다.
- [ ] 종료 후 카메라·HUD·입력이 복원되고 전투가 정상 시작된다.

## 4. 표시·연출 개선 항목

### UX-01. 영역형 버프 아이템의 범위 이펙트

#### 요구사항

헬로 월드 발신기처럼 영역형 버프를 제공하는 아이템을 소지하고 효과가 활성화돼 있을 때, 소지자 주변에 버프 이펙트를 표시한다.

예시: **`Hello world`라고 적힌 원형 고리가 플레이어 주변을 회전한다.**

다른 플레이어에게도 기본적으로 버프 범위가 보이며, 설정창에서 이를 켜고 끌 수 있어야 한다.

#### 현재 근거와 작업 범위

기존 실행 기록에는 헬로 월드 발신기 지급 후 다른 세 명의 공격력 증가, 18유닛 범위 이탈 시 해제, 재진입 시 재적용, 서버와 네 클라이언트의 수치 일치가 확인됐다고 적혀 있다. 이는 당시 후보의 검증 기록이며, 현재·후속 후보에서도 회귀 검증이 필요하다. [S1]

이번 작업은 해당 버프 판정을 새로 만드는 것이 아니라 **효과 활성 상태와 적용 범위를 시각적으로 전달하는 기능을 보강하는 것**이다.

#### 구현 방향

- 표시 위치와 크기는 실제 효과의 중심·범위 데이터를 따른다. 표시용 반경을 별도로 하드코딩하지 않는다.
- 최소 설정 항목은 `아군 버프 범위 표시`로 두고 기본값을 켬으로 제안한다.
- 타인의 범위 표시 여부는 각 사용자의 로컬 설정으로 적용한다.
- 표시 옵션은 시각 효과만 변경하며 실제 버프 판정이나 다른 사용자의 설정에 영향을 주지 않는다.
- 소지·활성화·제거 조건은 기존 효과 규칙을 그대로 따르고, 이펙트도 같은 수명을 갖게 한다.
- 표시를 위한 매 프레임 네트워크 전송은 피하고 기존 동기화 상태·위치를 활용한다.

#### 완료 기준

- [ ] 소지자의 실제 효과 활성 상태와 범위 고리 표시가 일치한다.
- [ ] 다른 세 명도 기본 설정에서 범위를 볼 수 있다.
- [ ] 한 사용자가 옵션을 꺼도 해당 화면의 표시만 꺼진다.
- [ ] 옵션을 꺼도 실제 능력치 증가·범위 이탈 해제·재진입 적용은 유지된다.
- [ ] 여러 소지자가 동시에 효과를 켜도 중복 생성·잔류·심한 시야 방해가 없다.
- [ ] 아이템 제거, 사망·부활, 재접속, 씬 이동 시 기존 효과 규칙에 맞게 표시가 정리된다.

### UX-02. 웨이브 진행과 전원 처치 표시

#### 요구사항

전투 씬에 `웨이브 1/5`처럼 현재 웨이브와 총 웨이브 수를 표시한다. 마지막 적을 처치해 전투를 끝냈을 때는 `전원 처치!` 또는 `Go!`처럼 다음 행동을 직관적으로 알린다.

#### 코드·기록 근거

`NetworkEnemyWaveSpawner`의 `currentWave`, `completedWaveCount`, `sessionPhase`는 동기화 상태다. 반면 `activeWaveCount`와 `aliveEnemies`는 서버에서 관리되며, `AliveEnemyCount`는 해당 목록을 세는 속성이다. 원격 클라이언트가 서버 전용 목록을 그대로 읽어 완료를 판단하는 방식은 피해야 한다. [S6]

#### 구현 방향

| 상황 | 표시 제안 |
|---|---|
| 전투 시작·진행 | `웨이브 1/5`, `웨이브 2/5` 등 |
| 중간 웨이브 종료 | `다음 웨이브 준비` |
| 마지막 웨이브 완료 | `전원 처치!` 또는 `Go!` |
| 다음 행동 안내 | 포털·다음 진행 방향을 식별할 수 있는 표시 |

- 총 웨이브 수는 실제 확정된 웨이브 구성을 기준으로 클라이언트에 전달한다.
- 최종 완료 표시는 서버가 확정한 세션 완료 상태에 연결한다.
- 적 생성 대기·실패로 화면에 적이 잠시 없는 상태를 전원 처치로 오인하지 않는다.
- 재접속 시 현재 상태는 복구하되, 과거 완료 알림을 중복 재생하지 않는다.

#### 완료 기준

- [ ] 네 클라이언트에 동일한 현재·총 웨이브가 표시된다.
- [ ] 중간 웨이브 종료와 최종 전투 완료가 명확히 구분된다.
- [ ] 적 생성 지연·재시도 중 잘못된 `Go!` 표시가 나타나지 않는다.
- [ ] 최종 완료 알림이 정상적으로 한 번 표시된다.

### UX-03. 퀘스트 완료 피드백

#### 요구사항

퀘스트를 완료했을 때 완료 사실을 즉시 알아볼 수 있게 한다.

#### 구현 방향

- 완료 순간 눈에 띄는 알림을 표시한다.
- 퀘스트 목록에도 완료 상태를 남겨 순간 알림을 놓쳐도 확인할 수 있게 한다.
- 별도 보상 수령이 필요한 구조라면 `목표 달성`, `보상 수령 가능`, `수령 완료`를 구분한다.
- 개인 퀘스트·공유 퀘스트의 기존 규칙을 유지하고, 올바른 플레이어에게 알림을 보낸다.
- 이미 본 알림은 UI 재열기·재접속·씬 이동 때 반복하지 않는다. 지속 상태 표시는 복구한다.

#### 완료 기준

- [ ] 완료 순간 알림과 목록 상태가 일치한다.
- [ ] 다른 플레이어의 개인 퀘스트 완료를 자신의 완료로 표시하지 않는다.
- [ ] 실제 보상 수령 상태와 화면 상태가 일치한다.
- [ ] 재접속·씬 이동으로 완료 상태가 사라지거나 알림이 중복되지 않는다.

## 5. 라이플 밸런스 개선

### 사용자 의견

라이플이 다른 두 무기 유형에 비해 너무 약하게 느껴진다. 각 발의 피해는 낮추되 연사력을 높이는 방향을 고려한다.

### 작업 원칙

**전용서버에서의 발사·명중 누락이나 공격 간격 문제를 먼저 배제한 뒤 수치를 조정한다.** 기능 결함으로 약해진 상태를 단순 피해량 상향으로 덮지 않는다.

### 비교 조건과 측정 항목

| 구분 | 기준 |
|---|---|
| 캐릭터 | 동일 레벨·공격력·장비 등급·강화 조건 |
| 추가 효과 | 버프·고유효과·치명타 등 결과에 영향을 주는 조건을 통제하거나 별도 기록 |
| 표적 | 같은 적·거리·방어 조건 |
| 환경 | 전용서버 + 4 Client와 Host + 원격 Client 3개의 같은 후보 |
| 측정 | 실제 발사 수, 명중 수, 발사 간격, 일정 시간 누적 피해, 처치 시간 |
| 후속 영향 | 연사 증가에 따른 고유효과 발동, VFX·SFX 수, 네트워크 처리량 확인 |

먼저 현재 수치의 기준선을 기록하고, 이후 발당 피해 감소·연사력 증가 후보를 비교한다. 구체적인 수치 변경은 측정 후 결정한다.

### 완료 기준

- [ ] 체감 약화가 수치 문제인지, 발사·명중 누락인지 구분됐다.
- [ ] 다른 두 무기 유형과 동일 조건에서 비교 결과를 기록했다.
- [ ] 고연사 방향의 플레이 감각과 누적 피해가 의도에 맞는다.
- [ ] 고유효과 과다 발동, 이펙트 과다 생성, 원격 발사 누락이 발생하지 않는다.

## 6. 남은 고유효과·Mirror 개선 병행

새 고유효과는 기존 싱글·멀티 공통 판정과 표시 구조를 우선 활용한다. 서버 판정만 확인하거나 소유자 화면만 확인한 상태를 완료로 기록하지 않는다.

| 점검 영역 | 확인 내용 |
|---|---|
| 실제 판정 | 피해·버프·범위·지속 시간이 서버 기준으로 올바른가 |
| 소유자 표시 | 발동·종료·범위가 소유자에게 보이는가 |
| 다른 플레이어 표시 | 다른 세 명에게도 필요한 정보가 보이는가 |
| 중복·수명 | Host 중복 발동, 풀 반환 오류, 씬 전환 후 잔류가 없는가 |
| 성능 | 여러 플레이어의 동시 발동 시 생성량과 화면 부담이 허용 가능한가 |

같은 공통 판정·UI·표시 파일을 동시에 수정하는 작업은 담당과 반영 순서를 조정한다. 기능별 검증과 통합 후 검증을 구분해 기록한다.

### 기존 기록에서 함께 확인할 위험

기존 전용서버 4인 실행 기록에 아래 후속 조사 대상이 남아 있다. [S1]

- 클라이언트 이펙트 풀 반환 중 `NullReferenceException`.
- 재접속 후 원격 플레이어 위치 불일치.

첫 번째는 새 이펙트 추가 전에 원인과 발생 경계를 확인한다. 두 번째는 영역형 버프의 보이는 위치와 실제 서버 판정 범위가 일치하는지 함께 점검한다. 두 현상의 구체적인 원인이나 서로의 인과관계는 아직 확정된 것으로 취급하지 않는다.

## 7. 전용서버·호스트 비교 테스트

### 환경별 목적

| 환경 | 인원 | 목적 |
|---|---|---|
| 전용서버 + 4 Client | 서버 1개, 플레이어 4명 | 사용자 관찰 증상의 주된 재현·완료 판정 |
| Host + 원격 Client 3개 | 호스트 플레이어 1명, 원격 플레이어 3명 | 호스트에서만 정상인 문제와 원격 클라이언트 차이 확인 |
| 싱글플레이 | 플레이어 1명 | 기존 화면·연출·입력·판정의 회귀 확인 |

**Host 1인 확인은 Host + 원격 Client 3개 비교를 대체하지 않는다.** 또한 같은 PC의 독립 프로세스 검증은 다중 PC나 Linux 서버 검증과 구분해 기록한다.

### 공통 실행 조건

- 서버와 클라이언트가 동일한 코드·자산 후보 및 호환 프로토콜을 사용하는지 기록한다.
- 해상도, 그래픽 설정, 언어, 캐릭터 구성, 장비, 버프 상태를 맞춘다.
- UI 문제는 동일 화면 조건에서 먼저 비교하고, 이후 해상도 차이를 추가 검사한다.
- 설정이 프로세스 간 공유되는 환경이라면 옵션 파일 경합 여부를 별도로 확인한다.
- 버그 수정마다 대상 씬과 진입 경로를 기록하고, 이후 씬 재진입·재접속을 검사한다.
- 소유자·다른 플레이어의 화면과 서버 상태를 구분해 증거를 남긴다.

## 8. 기존 코드 구현 지침

1. **기존 코드와 자산을 먼저 읽고 재사용한다.** 현재의 변수·메서드 이름, 문법, 이벤트 흐름, 씬 배선을 우선 따른다. 기능이 비슷하다는 이유로 새 관리 클래스를 추가하지 않는다.
2. **팀원 코드의 변경에는 `SW 수정 :` 형식의 쉬운 설명을 남긴다.** 변경 이유와 동작을 간단히 설명하고, 기존 주석은 필요한 이유 없이 지우지 않는다.
3. **불필요하거나 모호하거나 지나치게 어려운 이름과 구현을 추가하지 않는다.** 임의의 축약어, 의미 없는 래퍼, 과도한 추상화보다 팀원이 이해하고 추적할 수 있는 구조를 사용한다.
4. **버그의 원인을 좁혀 최소 범위로 수정한다.** UI 가림을 무조건 큰 정렬 숫자로 덮거나, 연결 누락을 무제한 검색·폴백으로 숨기지 않는다.
5. **서버 판정과 로컬 표시를 분리한다.** 버프 표시 옵션은 실제 효과를 바꾸지 않으며, 웨이브·퀘스트 완료는 올바른 상태에 연결한다.
6. **기존 기능과 연결을 보존한다.** GUID·Inspector 참조·UnityEvent·AnimationEvent·소유자 연결을 확인하고, 관련 없는 이름 변경이나 재구성을 섞지 않는다.
7. **검증 수준을 정확하게 기록한다.** 컴파일 성공, 오브젝트 생성, Host 정상, 네 클라이언트의 실제 화면 정상은 서로 다른 결과다. 미검증 항목은 완료로 처리하지 않는다.

주석 예시:

```csharp
// SW 수정 : 설정창이 열려 있는 동안 뒤쪽 단축키 안내가 확인 버튼을 가리지 않도록 숨긴다.
```

## 9. 최종 완료 체크리스트

- [ ] 멀티 인벤토리를 최신 디자인으로 맞췄다.
- [ ] 설정창·확인창·인벤토리를 HUD와 미니맵이 가리지 않는다.
- [ ] Act1 네 명의 밀려나는 연출이 네 클라이언트 모두에서 보인다.
- [ ] Act2 인트로 연결을 복구하고 손으로 잡아채는 동작을 자연스럽게 조정했다.
- [ ] 영역형 버프의 실제 범위와 이펙트가 일치하고, 타인 범위 표시를 로컬 설정으로 제어한다.
- [ ] 웨이브 진행과 최종 전원 처치를 구분해 표시한다.
- [ ] 퀘스트 완료와 보상 상태를 직관적으로 알 수 있다.
- [ ] 라이플의 기능 문제를 배제하고 동일 조건의 밸런스 비교를 기록했다.
- [ ] 새 고유효과와 기존 이펙트의 중복·잔류·풀 반환 문제를 점검했다.
- [ ] 전용서버 + 4 Client, Host + 원격 3명, 싱글 회귀 결과를 각각 기록했다.
- [ ] 남은 결함과 미검증 환경을 완료 항목과 구분했다.

> **최종 기준: “호스트에서 된다”가 아니라, “전용서버에 접속한 네 명 모두에게 올바르게 보이고 작동하며 싱글도 유지된다.”**
