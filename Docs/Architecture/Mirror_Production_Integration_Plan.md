# 기존 싱글을 보존하는 Mirror 단계별 정식 통합

> 2026-09-20 계획을 바탕으로, 2026-09-23 사용자 요청에 따라 단일 씬 통합·초기 로딩·시험 자산 완전 정리 방향을 반영한 현행 계획이다.
> 단계별 착수·조사·수정·검증·남은 작업은 [실행 기록](Mirror_Production_Integration_Execution.md)에 누적한다.
> 2026-09-23 최신 인계: 5·6단계 연결, 정식 이름·경로 이전과 Firebase 저장 보호를 구현했고 Unity 재컴파일 성공을 확인했다. 사용자 요청으로 새 빌드와 최종 플레이 검증은 집에서 이어간다. 단계 완료 판정은 보류한다. 최신 상태·빌드 방법·남은 검증은 실행 기록 §9.6을 우선하며, §9.1~9.5는 앞선 중단 시점의 이력이다. 문서 정리 후 변경을 기능별 커밋하고 Push는 하지 않는다.
> 실행 시 에이전트 운영은 현재 `AGENTS.md` §1-2를 따른다. 주 에이전트가 계획·구현 채택·최종 Unity 검증을 소유하고, 범위가 명확한 읽기 조사는 지정된 `unity_scout`에 위임한다. 아래 Luna 및 Sol xhigh 표기는 계획 수립 당시의 검증 이력이다.

## 1. 조사·검증 결론과 전환 방향

**기존 싱글 씬과 게임 규칙을 공통 원본으로 사용하고, 멀티 플레이에서만 Mirror 세션·서버 권한·동기화 계층을 활성화합니다.** 맵을 싱글용·멀티용으로 복제하여 유지하는 방침은 폐기합니다.

확정한 운영 방식은 다음과 같습니다.

- 오프라인 싱글 실행을 유지합니다.
- 이번 정식 목표는 **로비 → Act1 전체·보스 → Act2 전체·보스 → 결과 → 로비 복귀·새 런**입니다. 2026-09-23 사용자 확정 범위이며 Act3는 후속 확장입니다.
- 진입 UI에서 싱글·멀티 모드를 선택하되 StageSelect·전투·캠프·이벤트·보스·결과의 실제 콘텐츠 씬은 공용화합니다. 멀티 로비의 명부·준비 UI처럼 고유한 기능은 유지하되 같은 맵을 별도 씬으로 복제하지 않습니다.
- 정식 완료 시 프로젝트에서 관리하는 코드·씬·프리팹·SO·설정·Editor 도구에 `MirrorTest` 및 동일 목적의 시험 명칭·의존성이 하나도 남지 않아야 합니다. 필요한 네트워크 기능은 정식화하고 불필요한 시험 자산은 제거합니다. 단순히 빌드에서 제외하거나 이름만 바꾸는 것으로 완료하지 않습니다.
- 신규 고유효과 확장보다 기존 기능의 공통화와 회귀검증을 먼저 진행합니다.

현재 **1~4단계는 완료**이며 기존 검증과 사용자 수용 범위를 유지합니다. 아래 최초 조사표는 **2026-09-20 당시의 차이**이고 현재 미해결 목록이 아닙니다. Context 필수 조건 분리, 포션 1초 제한, 공통 피해 계산과 스킬·연출 연결에 이어 10종 효과 공통화와 **B04 정상 패시브 부활**을 반영했습니다. 4단계 결과·제한은 [실행 기록 §8](Mirror_Production_Integration_Execution.md#8-4단계--2026-09-23), 남은 5~6단계 방향은 같은 문서 §7을 따릅니다.

최초 Luna 조사 결과는 당시 요청한 **Sol xhigh로 한 차례 교차 검증**했습니다. 주요 구조 판단은 확인됐고, 두 항목은 정정했습니다.

| 조사 항목 | 최종 판단 |

| 싱글·미러 피해 계산이 별도로 존재 | 확인. 계산과 효과 처리 변경이 양쪽에서 달라질 수 있습니다. |

| 미러 피해 결과에 일부 피격 연출 정보가 없음 | 별도 RPC 연출도 존재합니다. 전체 VFX 소실로 단정하지 않고 실제 연출을 대조합니다. |

### 1.1 오늘의 실행 범위와 순서

2026-09-23 사용자 최종 확정 범위는 **Act2까지 정식 통합을 5→6단계로 끝내는 것**입니다. Act1 보스 이후 Act2로 진행하고 Act2 보스 이후 결과·복귀·새 런을 검증합니다. 공용 씬 전환을 7단계로 미루지 않습니다. 서버 권한·싱글 동작·초기 로딩·시험 의존성 제거를 생략하거나 미검증을 완료로 표시하지 않습니다. Act3의 기존 싱글 동작은 보존하며 멀티 연결은 7단계 후속 확장으로 남깁니다.

1. 현재 작업 트리의 고유효과·팀원 싱글 변경을 해당 호출 흐름과 대조하고, 이번에 공유할 규칙과 남길 네트워크 처리를 확정합니다. 1~3단계 전체를 처음부터 반복하지 않습니다.
2. 4단계에서 완료 고유효과를 공통 실행에 연결하고 B04를 닫습니다. 초기 표시 문제의 원인 확인과 준비 완료 조건도 이때 확정합니다.
3. 5단계에서 기존 싱글 씬으로 경로를 전환하고, 초기 로딩과 모드별 실행 주체를 연결합니다. 사용자가 확인한 Stage1 왕복을 바탕으로 Act1·Act2 전 구간에 같은 경계를 적용합니다.
4. 6단계에서 결과·복귀·새 런, 정식 명칭·경로·참조 및 시험 자산 제거를 마치고, 최종 후보 빌드로 실제 싱글·멀티를 확인합니다. 같은 후보 빌드로 초기 로딩·고유효과·씬 진행 검증을 함께 수행합니다.

씬 복제를 없애면 맵 수정의 이중 관리와 불필요한 씬 데이터는 줄어듭니다. 공유 텍스처·메시까지 현재 빌드에 두 벌 들어 있다는 뜻은 아니므로 용량 감소량을 미리 단정하지 않습니다. 필요한 최종 빌드의 기존 BuildReport로 포함 씬·의존성만 확인하며, 용량 측정만을 위한 별도 빌드를 추가하지 않습니다.

## 2. 단계별 통합 계획

### 0단계 — 현재 동작과 차이부터 고정

- 현재 미커밋 변경을 보존하고, 싱글 원본·미러 복제본의 차이를 **공유할 게임 규칙 / 네트워크 처리 / 시험 도구**로 정리합니다.
- 포션 재사용 제한처럼 싱글에만 추가된 기능과, 최신 고유효과처럼 미러에 먼저 구현된 기능을 양방향으로 비교합니다.
- 실제 Fighter·Gunner의 공격, 장착, 포션, 사망·부활, 캠프 거래를 기준 동작으로 기록합니다.

**완료 조건:** 각 기능의 상태 소유자와 실제 호출 경로가 명확하고, 통합하면서 보존할 동작이 정리돼 있어야 합니다. 이 단계에서는 이름 변경이나 대량 이동을 하지 않습니다.

### 1단계 — PlayerContext와 플레이어 소유 상태 정리

- `PlayerContext`는 해당 플레이어의 인벤토리·장비·지갑·Stat·체력·마나·버프·컨트롤러 참조를 제공하도록 정리합니다.
- `RuntimeStateSync`, `CombatAuthority` 같은 네트워크 전용 컴포넌트는 공통 `IsComplete`의 필수 조건에서 제외하고 각 컴포넌트에서 검증합니다.
- 싱글의 기존 `Instance` 호출은 일괄 제거하지 않습니다. 통합하는 기능부터 자기 플레이어의 참조를 사용하도록 바꾸고, 새 전역 `CurrentPlayer`는 만들지 않습니다.
- UI는 기존 `InventoryView.Bind(PlayerContext)` 등 연결 API를 재사용합니다.

**완료 조건:** 싱글은 Mirror 세션 없이 실행되고, 멀티 4명의 장비·자원·UI가 서로 섞이지 않아야 합니다. 재접속·씬 이동 후 구독과 UI 연결도 한 번만 유지돼야 합니다.

### 2단계 — 포션·장비·인벤토리·경제 규칙 통합

- 포션은 기존 원본의 사용 조건·효과·충전·재사용 제한을 공통 규칙으로 사용하고, 미러는 요청 전달과 서버 검증·결과 동기화를 담당합니다.
- 장착, 거래, 강화는 기존 `EquipmentSystem`, 거래·강화 서비스의 규칙을 재사용합니다. 서버 스냅샷 반영과 실패 시 복구는 네트워크 쪽에 유지합니다.
- 싱글 UI는 기존 직접 호출을 유지하고, 멀티 UI는 기존 외부 입력 연결을 통해 요청합니다. Host도 서버 확정 전에 아이템이나 골드를 먼저 변경하지 않습니다.
- 요청 번호·상태 버전·소유권·중복 구매 검사는 필요한 안전장치이므로 간결화를 이유로 제거하지 않습니다.

**완료 조건:** 이동·교환·장착·해제·판매·구매·강화·드롭·획득이 양쪽에서 같은 규칙으로 동작해야 합니다. 동시 구매는 한 명만 성공하고, 실패·재접속으로 아이템이나 골드가 복제되지 않아야 합니다.

### 3단계 — 기본 공격·스킬·상태이상 처리 통합

- 기존 `WBH_CombatManager.ProcessDamage` 호출 계약을 보존하면서, 양쪽에서 중복된 피해 계산을 공용 메서드로 모읍니다. 새 전투 Manager는 만들지 않습니다.
- 미러의 서버 요청 검증, 공격 ID, 공격 시점 스탯 보존, 후속 피해 큐는 유지합니다. 이를 싱글 호출부마다 복사하지 않습니다.
- 기존 `WBH_DamageRequest/Result`를 활용해 피해 종류·공격 출처·피격 위치·연출 정보를 전달합니다.
- 적 AI·피해·사망·보상은 멀티에서 서버가 확정하고, 클라이언트는 전달받은 상태와 연출을 표시합니다. 싱글 적 드라이버와 미러 드라이버의 동시 실행을 막습니다.
- Fighter·Gunner의 현재 구현된 액티브 스킬과 진화·강화 분기를 명시적으로 포함합니다. 원본 스킬 실행·비용·쿨다운 규칙을 재사용하고, 기본 공격과 스킬 각각의 검증표를 유지합니다.
- 같은 장비·스탯·조준·대상·프레임 조건에서 입력 반응, 선딜·타격·후딜, 차징 시작/해제, 이동·투사체·다단히트, VFX·SFX의 종류·위치·크기·시작/종료를 싱글·Host·원격 클라이언트에서 대조합니다. 마나·쿨다운·스택, 피격·이동·무기 교체·사망·끊김에 의한 취소와 정리도 확인합니다.
- 네트워크 전달 지연과 게임 코드가 추가하는 지연을 분리해 기록합니다. 클립·이벤트 데이터 일치만으로 연출 동등성을 선언하지 않고 실제 시간 측정과 화면 비교를 수행합니다. 네트워크 시간을 감안해도 눈에 띄는 지연이나 연출 누락·중복·불일치가 남으면 완료로 처리하지 않습니다.

**완료 조건:** 같은 장비·Stat·적 조건에서 기본 공격과 구현된 스킬·진화의 피해·자원·타이밍·연출 규칙이 일치하고, 직접타·스킬·추가타·DoT의 처치 귀속과 보상이 한 번만 처리돼야 합니다. 공격·스킬·피격·사망·파괴 연출을 실제 화면으로 확인하며, 네트워크 전달 시간을 제외한 눈에 띄는 지연 차이가 없어야 합니다. 미구현 분기와 미검증 조건은 검증표에서 명확히 구분합니다.

### 4단계 — 현재 완료 고유효과 10종 공통화·정상 부활

- 현재 완료 구현은 **10종**입니다. Q1의 아크 블레이드·인페르노·유리빛 궤도·절전모드 헤드셋·폐기된 부스터 모듈·마나 중계기 6종에, 이후 완료된 **태양의 은혜·밤의 칼날·중력 우물·특이점 박격포**를 포함합니다. 107단계는 이전 6종의 검증 이력이며 추가 4종이나 정식 통합의 완료 증거가 아닙니다.
- 착수 시 현재 효과 SO·아이템 연결·실제 호출부와 최근 Diff를 대조해 이 10종의 최신 동작을 보존합니다. 이후 추가·수정된 기능이 있으면 보존 대상으로 기록하고, 과거 복제 코드로 덮어쓰거나 조용히 제외하지 않습니다. 이번 묶음에서 새 효과를 설계하지 않습니다.
- 완료 효과를 한 종씩 싱글과 미러의 공통 실행 경계에 연결합니다. 3단계에서 공통화한 `WBH_CombatManager.CalculateDamage`, 공격 출처·스냅샷·후속 큐와 원본 스킬 API를 재사용합니다.
- 발동 조건·효과 계산·아이템별 상태는 플레이어가 소유하고, 미러 전용 코드는 요청 검증·동기화·원격 연출을 담당하도록 정리합니다.
- SO에 플레이어별 쿨타임이나 누적 상태를 저장하지 않습니다.
- `DamageCause`의 Direct/Skill/Effect/DoT 자격과 AttackId를 보존합니다. 투사체는 발사 시 무기·효과·속성·연출을 보존하고, 피해 스탯은 기존 동작대로 적중 시 캡처해 같은 처리의 후속 피해 큐까지 공유합니다. 예약 폭발은 기폭 시점 스탯을 사용합니다. 다중 Collider 중복 차단, 추가 4종의 보호막 흡수·준비공격 단일 소비·장판/예약 폭발 상한과 수명·교체 후 유지/사망 시 정리도 공통 규칙에 포함합니다.
- 공통화한 효과가 검증되면 대응하는 복제 로직을 제거합니다. 두 구현을 계속 수정하는 상태를 남기지 않습니다.
- B04 정상 패시브 부활을 이 단계의 필수 후속으로 처리합니다. 기존 횟수 차감·패시브 HP 비율·무적·애니메이션 종료·입력 복구 규칙을 공유하고 멀티에서는 서버만 확정합니다. `ServerReviveForTest` 호출로 대체하지 않으며, 동시 사망/끊김·재접속에서 중복 차감·부활이 없어야 합니다.

**완료 조건:** 완료 10종과 착수 시 확인한 기존 변경이 실제 싱글·서버 공통 규칙을 사용하고, 장비 교환·가방 이동·사망·정상 부활·재접속·새 런에서 상태가 정확히 유지되거나 초기화돼야 합니다. 효과별 실제 발동·소비·종료와 원격 표시를 확인하고, 이전 Q1 및 추가 4종의 검증 기록에서 바뀐 효과·소유 경계에 필요한 검사를 가져옵니다. 단순히 과거 107단계 수를 맞추기 위해 전체 검사를 반복하지 않습니다.

오늘은 정식 통합을 우선하므로 **신규 고유효과 개발은 6단계 채택 후** 재개합니다.

**2026-09-23 결과:** 공통 실행기와 플레이어별 상태를 연결하고 싱글·Editor Host·별도 Player에서 변경 경계를 검증했습니다. 정상 부활의 HP 비율·10초 무적·원본 클립 종료, 재접속 중/완료 후 횟수 보존과 부재 중 종료 후 입력 복구를 확인했습니다. 초기 표시의 자산·풀·GPU 준비 조건은 정리했으며 실제 로딩 연결과 새 Player 첫 표시 검증은 5단계에 남깁니다. 이후 Editor에서 가능한 검증은 Editor에서 수행하고, 매 수정마다 Player를 재빌드하지 않습니다.

### 5단계 — 기존 싱글 씬 공용화·초기 로딩·Act1·Act2 연결

- 기존 미러 세션의 명부·준비·투표·재접속·서버 씬 전환을 재사용합니다. 별도 세션 Manager를 추가하지 않습니다.
- `Assets/Scenes/Maps`의 기존 정식 씬을 공통 콘텐츠 원본으로 사용합니다. 기존 Mirror route 허용 목록을 이 경로로 연결하고, 시험 씬에만 있던 필수 스폰 위치·UI·사운드·네트워크 참조는 공통 씬/작은 세션 구성에 이식합니다. 지형·배치·NavMesh·광원·웨이브 데이터를 다시 복제하지 않습니다.
- 모드는 진입 시 확정하고 **씬의 스포너·저장·웨이브가 동작하기 전에** 적용합니다. 기존 NetworkManager·SessionLifecycle과 명시적으로 연결된 참조로 결정하며, 씬 이름의 `MirrorTest` 포함 여부나 뒤늦은 `Find`/다음 프레임 끄기에 의존하지 않습니다. 연결 준비 중과 종료 중도 멀티 세션 상태로 다뤄 오프라인 경로가 순간 실행되지 않게 합니다.
- “Mirror 계층을 얹는다”는 것은 멀티 진입 때 세션 구성과 등록된 네트워크 프리팹/어댑터를 사용한다는 뜻입니다. 생성·동기화가 시작된 객체에 `NetworkIdentity`/`NetworkBehaviour`를 임의로 추가하거나 컴포넌트 순서를 변경하지 않습니다. 기존 원본 기반 프리팹 Variant·공유 Animator/머터리얼/효과를 우선하고 게임 규칙과 맵의 복제본을 만들지 않습니다.
- StageSelect는 기존 `StageMapSaveData`와 복원 API를 사용합니다. 멀티에서는 선택 의도만 전달하도록 명시적인 외부 제어 경계를 추가해, private 필드 리플렉션과 다음 프레임 보정에 의존하는 연결을 정리합니다. 싱글 기본 동작은 유지합니다.
- 캠프 NPC는 기존 Inspector `UnityEvent` 연결을 우선 사용합니다.
- 최신 싱글 맵의 스폰·웨이브 원본 데이터를 공유하고 아래 실행 주체를 상호 배타적으로 선택합니다. 클라이언트에서 비활성화할 게임 로직과 유지할 풀·VFX·SFX 표시를 구분합니다.

| 책임 | 오프라인 싱글 | 멀티 서버 / Host | 원격 클라이언트 |

#### 5.1 첫 진입의 하늘색 사각형과 준비 완료 조건

사용자가 명확히 한 증상은 **Editor에서 첫 게임 진입 후 스킬이 잠시 파란색/하늘색 사각형으로 보이는 현상**입니다. 정상 청색 이펙트나 분홍색 오류 표시를 뜻하지 않습니다. **실제 빌드한 Player에서의 발생 여부는 미확인**이며 필요한 최종 빌드에서 확인합니다.

- Unity 6.3은 Editor의 비동기 셰이더 variant 컴파일 중 cyan 임시 셰이더를 사용합니다. 이 설명은 보고된 현상과 부합하지만 실제 대상 머터리얼/컴파일 상태는 구현 시 확인해야 합니다. 이는 Editor의 Game/Scene View 기능으로, Player의 Addressables 다운로드 대기와 동일시하지 않습니다. [Unity 비동기 셰이더 컴파일](https://docs.unity3d.com/6000.3/Documentation/Manual/AsynchronousShaderCompilation-introduction.html), [Editor 전용 설정 범위](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/EditorSettings-asyncShaderCompilation.html).
- 기존 Editor 작업에서 해당 스킬의 첫 표시와 셰이더 컴파일 완료 후 표시를 대조합니다. Player 검증에서는 새 프로세스 최초/두 번째 발동의 화면·첫 사용 지연을 확인합니다. 증상이 실제 Player에서도 나오면 해당 프리팹의 텍스처/알파·머터리얼·variant 포함과 로드/풀 준비/첫 표시 시각을 좁혀 조사합니다. Editor 현상만으로 Player 결함이나 전면 Addressables 전환 필요성을 확정하지 않습니다.
- 기존 시작/SceneLoader·로딩 UI와 기존 스포너 초기화에 준비 완료 조건을 연결합니다. 순서는 **모드 확정 → 데이터·씬 로드/활성화 → 필요한 자산·풀 및 플레이어/Context·HUD 준비 → 입력·웨이브 허용**입니다. 스폰 후 얻는 참조를 씬 활성화 전에 기다리지 않습니다. 기존 페이드/로딩 표시를 목적 씬 활성화 뒤에도 필요한 준비가 끝날 때까지 유지하고, 무기 외형의 비동기 완료도 필요한 준비 목록에 포함합니다. 고정 초/프레임 대기로 대신하지 않습니다.
- 이번 런의 Fighter/Gunner·선택 스킬과 진화, 장착 무기, 동료의 원격 표시, 해당 씬에 필요한 효과·투사체·SFX만 준비합니다. 전 스킬·전 맵을 한 번에 로드하지 않습니다. 프리웜은 피해·보상·소리·화면 노출 없이 필요한 풀 인스턴스를 준비하고 반환합니다. 셰이더 첫 사용 비용이 확인된 경우에만 해당 렌더링 경로를 추가 준비합니다.
- Mirror의 프로토콜 Ready/스폰과 **게임플레이 준비 완료**를 구분합니다. 플레이어 스폰 전 Context를 기다리며 프로토콜을 막는 교착을 만들지 않습니다. 자산·스폰·바인딩이 완료된 참가자만 게임플레이 준비를 알리고, 서버는 현재 씬 전환 번호와 참가자 소유권을 확인한 뒤 입력/전투를 허용합니다. 늦은 접속·재접속에도 적용하고 Host에서 두 번 초기화하지 않습니다.
- 실패·취소·끊김·제한시간 초과는 준비 성공으로 처리하지 않습니다. 입력·웨이브를 잠근 채 원인을 표시하고 기존 재시도/로비 복귀 흐름으로 정리합니다. 이전 씬의 늦은 완료 콜백은 무시하고 핸들·풀·UI 구독을 해제합니다. 전용 서버는 게임 데이터 준비가 필요하지만 화면용 VFX/SFX/GPU 프리웜을 기다리지 않습니다.

**수용 조건:** Editor 컴파일 중 임시 표시와 실제 Player 결과를 구분해 기록합니다. 실제 빌드의 새 프로세스 첫 진입과 재진입에서 같은 스킬의 색·텍스처·표시가 정상이고, 준비 중 입력으로 마나/쿨다운/피해가 소비되지 않아야 합니다. 싱글·Host·원격 화면을 필요한 통합 실행에 포함합니다. Editor 전용 컴파일 검사 API를 Player 코드에 넣지 않으며 전역 비동기 컴파일 설정을 임의로 바꿔 해결한 것으로 처리하지 않습니다.

#### 5.2 Addressables 확장 범위

현재 설치된 `com.unity.addressables`는 **2.8.1**입니다. 초기화는 카탈로그와 로더 준비이며 개별 무기·VFX 로드나 첫 렌더 완료를 보장하지 않습니다. [Unity 2.8 초기화 문서](https://docs.unity3d.com/Packages/com.unity.addressables@2.8/manual/InitializeAsync.html)를 기준으로 자산별 완료를 구분합니다.

현재 스킬 VFX는 `WBH_PlayerEffect`의 직접 참조 → `WBH_EffectSpawner` → `WBH_EffectPoolManager` 경로이며, 풀은 등록 목록을 사전 생성하고 없는 항목을 첫 요청 때 동기 생성합니다. 무기 외형 `PlayerWeaponVisualPresenter.InstantiateAsync`와 별개입니다. Addressables 설정값 `m_BuildAddressablesWithPlayerBuild=0`은 **PreferencesValue(사용자 환경설정 따름)**이고 자동 빌드 금지가 아닙니다. 기존 `MirrorLanTestBuilder.PrepareWindowsAddressables`의 명시적 콘텐츠 빌드·포함 확인을 정식 빌드 흐름에 이어받아, 동일 후보 Player와 맞는 콘텐츠가 포함되도록 합니다.

| 대상 | 이번 정식 통합 | 이후 확장 조건 |
|---|---|---|
| 기존 무기 외형 | 현재 Addressables 캐시·장착 버전·해제 흐름을 재사용하고 로딩 완료를 준비 조건에 연결 | 원격 장비 교체·재접속에서도 수명 일치 |
| 스킬 VFX·투사체의 시각 자산·SFX | 기존 직렬화 참조와 풀을 우선 사용; 문제 자산만 준비 | 실제 메모리/로딩 병목이 확인되면 캐릭터·효과 묶음으로 비동기 로드, 풀 수명 동안 핸들 유지 |
| 적 외형·파괴 VFX·맵별 큰 자산 | 현재 씬/풀 경로 유지 | Act별 사용 범위·메모리 근거가 생기면 분리. 실제 적과 파괴 연출의 풀 수명은 계속 분리 |
| 씬 전체·핵심 데이터/UI | 공용 씬 통합과 기존 시작 흐름 유지 | 별도 콘텐츠 배포나 메모리 요구가 생길 때 이관; 오늘 전면 Addressables 전환은 하지 않음 |

확장할 때는 로드한 소유자가 사용 종료 시 해제하며, 풀에 남은 인스턴스가 의존하는 핸들을 먼저 해제하지 않습니다. 취소·실패도 정리 대상입니다. [Unity 메모리 관리](https://docs.unity3d.com/Packages/com.unity.addressables@2.8/manual/memory-assets.html)를 따릅니다. `Resources`·씬의 직접 참조·Addressables 양쪽에 같은 의존성이 남아 용량이 늘지 않도록 해당 이관 묶음의 참조를 확인합니다. Addressable 자산은 `Resources` 밖으로 `.meta`와 함께 이동해야 합니다. [Unity 의존성 문서](https://docs.unity3d.com/Packages/com.unity.addressables@2.8/manual/AssetDependencies.html).

네트워크 프리팹까지 비동기화할 경우 클라이언트의 등록/로드가 스폰 메시지보다 먼저 끝나야 하며 서버와 같은 자산 ID·컴포넌트 구성을 유지해야 합니다. 이번에는 시각 자산 준비와 네트워크 프리팹 공급을 섞어 확대하지 않습니다. [Mirror 스폰 등록 규칙](https://mirror-networking.gitbook.io/docs/manual/guides/gameobjects/custom-spawnfunctions). GPU 프리웜은 Addressables와 별도 문제이며, 필요성이 확인될 때 로딩 구간에 한정합니다. [Unity 6.3 프리웜](https://docs.unity3d.com/6000.3/Documentation/Manual/shader-prewarm.html).

### 6단계 — 결과·복귀·정식 승격 및 MirrorTest 잔존 0건

- 검사기·Smoke·생성기도 예외 없이 정리합니다. 운영에 불필요한 것은 삭제하고, 계속 필요한 최소 회귀 검사/Editor 도구만 정식 명칭과 위치로 이전합니다. 테스트 타입을 유지하는 별칭·상속 껍데기·옛 씬 fallback을 남기지 않습니다.

## 3. 팀원 코드 수정·API 원칙

- 팀원 파일은 단계별로 **파일·수정 이유·싱글 영향**을 먼저 정리합니다. 실제 수정 직전에는 저장소 지침에 따라 대상 파일을 제시하고 `이 스크립트를 수정할까요?` 승인을 받습니다.
- 변경 지점에는 `SW 수정`을 표시하고, 변경 메서드의 XML `<summary>`에 동작을 쉽게 설명합니다.
- 기존 팀원이 작성한 주석은 변경 내용과 직접 충돌하지 않는 한 삭제하지 않습니다. 코드 이동·공통화 시에도 설명과 작성 의도를 적합한 위치에 보존하고, 실제 동작과 충돌하는 부분만 필요한 범위로 수정합니다.

```csharp
/// <summary>
/// SW 수정: 지정된 플레이어의 포션을 사용합니다.
/// 싱글의 재사용 대기시간을 유지하며, 멀티에서는 서버가 호출합니다.
/// </summary>
```

- 공개 API 추가는 플레이어 참조 연결, 공통 규칙 실행, StageSelect 외부 제어에 필요한 범위로 제한합니다.
- 기존 요청·결과 타입과 이벤트를 먼저 사용합니다. 구현 하나를 위한 인터페이스·Factory·Manager는 추가하지 않습니다.
- 메서드는 역할이 드러나는 이름을 사용하고, 의미 없는 전달 메서드나 긴 매개변수 연결을 만들지 않습니다. 기존 직렬화 필드명과 공개 호출 계약은 가능한 유지합니다.
- 단계 완료 보고는 **변경 내용 / 싱글 유지 방식 / 멀티 동작 / 검증 결과** 네 항목으로 요약합니다.

## 4. 검증과 채택 기준

단계별 검증 씬·빌더 목록·승인된 Build Settings는 6단계의 **대체 검증 → 정식 등록 교체 → 시험 자산 제거 → 최종 후보 검증** 순서로 종료합니다. 중간 단계 정리에서 삭제·원복하지 않습니다. 빌드가 자동으로 변경한 무관한 플랫폼 설정·내부 캐시는 별도로 복원할 수 있습니다.

검증은 해당 단계의 동작·권한·참조 변경을 직접 확인하는 데 한정합니다. 필요한 순서는 **오프라인 싱글 → Host+Client → 별도 서버+Client**이며, 이미 통과한 변경 없는 조합을 단계마다 모두 반복하지 않습니다. 최종 Act1 채택에는 다음을 포함합니다.

- Fighter·Gunner 혼합 4인, 실제 입력·전투·캠프 거래·전체 웨이브·보스.
- 사망·부활, 차징 중 끊김, 장비·버프 보유 재접속, 결과 화면 재표시와 새 런.
- 지연·중복 요청·동시 구매·잘못된 소유권 요청.
- 실제 다중 PC LAN 검증. 인터넷 배포를 목표로 할 때는 WAN 조건도 추가.
- 일반 적 동시 파괴와 보스 사망의 프레임 시간·풀 반환·시각 품질.
- 컴파일·Console 기준 비교, Missing Script, GUID·Prefab 참조, 서버·클라이언트 빌드 확인.
- 동일 공용 씬에서 모드 전환·첫 로딩·실패 정리, 정상 패시브 부활, 시험 의존성 제거 후 결과·복귀·새 런.

**불필요한 검증을 늘리지 않는 규칙:**

- 단계 수용 조건과 관계없는 다른 변경사항을 위한 추가 빌드·재검증, 검증용 생성기/검사기를 검증하기 위한 부차적 검사, 전체 씬 재생성·전수 반복 검사는 수행하지 않습니다. 생성 결과의 실제 참조와 게임 동작 검증은 필요한 검증입니다.
- 소스/Diff·컴파일·관련 참조 확인으로 충분한 변경은 그 수준에서 끝냅니다. 빌드는 Player에서만 확인할 문제, 네트워크/직렬화/자산 변경의 반영, 최종 공용 씬 채택에 필요할 때만 수행합니다. 테스트 코드 변경도 현재 수용 조건을 확인하는 데 꼭 필요할 때로 제한합니다.
- 한 최종 후보 빌드를 싱글·Host·전용 서버·첫 로딩 검증에 재사용하고, 이후 관련 코드/자산 변경이나 실제 실패가 있을 때만 영향 범위를 다시 빌드·검사합니다. 구형 실행 파일의 PASS로 새 버전 완료를 선언하지 않습니다.
- 3단계에서 사용자가 수용한 산탄 무작위성과 직선 표적 경계는 새 회귀 증거 없이 재검증하지 않습니다. 기존 보스 셰이더·MPPM·설정 파일 경합도 단계 동작을 막는 경우에만 필요한 원인을 처리하며 부수 과제로 확대하지 않습니다. 관련된 실제 오류를 기존 문제라는 이유로 통과시키지는 않습니다.
- LAN, 실제 전투, 첫 로딩, 사망·정상 부활·재접속·저장 분리 등 정식 동작을 증명하는 검증은 부차적 검증이 아닙니다. 수행하지 못하면 미검증으로 남깁니다. 동일 최종 실행에서 필요한 성능·파괴 연출도 함께 관찰하고, 성능 변경이나 이상 증거가 없으면 별도 최적화 실험을 추가하지 않습니다.

최초 2026-09-23 계획 개정은 **관련 구조 조사와 두 문서 수정**만 수행한 이력입니다. 이후 4단계 검증과 5·6단계 구현이 진행됐으며, 최신 인계 상태는 실행 기록 §9.6을 따릅니다. 현재 후보의 빌드·최종 플레이 검증은 집에서 이어가고, 이번 미완료 묶음의 개인 구현 로그는 아직 갱신하지 않았습니다.
