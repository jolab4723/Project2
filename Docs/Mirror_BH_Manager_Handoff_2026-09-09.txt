DataManager / SettingManager 팀원 전달 사항
작성일: 2026-09-09
담당 영역: BH

1. 현재 처리

사용자 지시에 따라 아래 두 원본 스크립트는 수정하지 않았습니다.
- Assets/WBHTest/Scripts/0. Core/Manager/DataManager.cs
- Assets/WBHTest/Scripts/0. Core/Manager/SettingManager.cs

기존 API를 유지해 Mirror 연결을 진행하고 있습니다. 서로 다른 PC에서는 각 PC의
로컬 저장을 사용할 수 있습니다. 같은 PC에서 여러 EXE를 실행할 때의 개인 저장은
별도 문제로 구분합니다. --mirror-profile은 재접속 정보와 키 바인딩을 구분하지만,
아래 매니저의 저장 경로를 나누지는 않습니다.

2. DataManager: 같은 PC 다중 EXE의 개인 패시브 저장 충돌

코드 경로:
GetSavePath(fileName) -> Application.persistentDataPath + 고정 파일명
SavePassiveData() -> SaveSinglePlayerSlot() -> profile_singleplayer.json

서로 다른 Mirror 프로필을 실행해도 위 저장 파일은 같습니다. 각 EXE에서 다른
패시브를 구매·저장하면 마지막 저장이 앞선 프로필을 덮어쓸 수 있습니다.
이 문제를 피하려고 구매·저장 로직을 SW에 복제하지 않았습니다.
현재 멀티 로비 패시브는 저장 분리가 준비되기 전까지 조회만 허용합니다.

확인 근거:
- 실제 Unity 실행에서 기존 GetSavePath의 결과가 persistentDataPath 아래의
  profile_singleplayer.json임을 확인했습니다.
- 동일 경로의 두 EXE가 동시에 덮어쓰는 시험은 수행하지 않았습니다.
- 사용자 저장 파일에 테스트 데이터를 쓰지 않았습니다.

최소 요청:
- 초기 로드 전에 실행 프로필별 저장 루트를 지정할 공개 API를 제공할지 검토해 주세요.
- 지정하지 않은 싱글플레이는 기존 경로와 저장 형식을 유지하면 됩니다.
- SW는 확정된 실행 프로필 이름으로 경로를 지정한 후 기존 로드/저장 API를 호출하겠습니다.

참고:
SaveMultiplayerSlot(index, data)는 명시적인 공유 슬롯 데이터를 받아 저장하므로
완성된 파티 저장 데이터에 재사용할 수 있습니다. 일반 SaveGameplayData는 로컬
싱글턴을 조회하므로 참가자 전원의 런 상태 저장을 자동으로 대신하지 않습니다.

3. SettingManager: 초기화 순서와 저장값 검증

코드 경로:
Activate() -> savePath 설정 -> Load() -> Apply() -> Save()
ApplyDisplay() -> resolutions[resolutionIndex], frameRates[targetFrameRate]

실제 Unity 검증:
- Activate 이전의 저장 경로는 null이며 기존 Save 호출이 ArgumentException으로 실패합니다.
- 검증용 별도 비활성 컴포넌트에 resolutionIndex = int.MaxValue를 설정하고
  ApplyDisplay를 호출하면 IndexOutOfRangeException으로 실패합니다.
- 두 예외는 검사 코드에서 포착했습니다. 화면 설정이나 사용자 파일은 바꾸지 않았습니다.
- 정상 시작 순서에서 항상 실패한다는 뜻은 아닙니다. Activate를 먼저 호출하고
  유효한 설정을 사용하는 흐름은 구분해야 합니다.

최소 요청:
- 설정 적용 전에 초기화가 보장되는 호출 순서 또는 공개 준비 상태를 제공해 주세요.
- JSON이 null/손상 상태이거나 해상도·FPS 인덱스가 범위를 벗어나면 기본값으로
  복구하도록 검사해 주세요.

4. SettingManager: 같은 PC 다중 EXE의 설정 저장 공유

Activate에서 persistentDataPath/settings.json을 고정 경로로 사용합니다.
서로 다른 --mirror-profile이라도 이 파일은 공유합니다. 또한 Load가 Apply를
호출하고 Apply가 Save를 호출하므로 시작만 해도 설정 파일을 다시 씁니다.
단순히 설정 UI를 열지 않는 것으로 파일 무변경을 보장할 수 없습니다.

최소 요청:
- 프로필별 저장 경로 지정 또는 저장을 생략하는 테스트용 경계를 검토해 주세요.
- 가능하면 설정 읽기, 런타임 적용, 파일 저장을 구분해 주세요.
- 파일 저장 실패와 손상 JSON의 복구 처리를 함께 확인해 주세요.

SW 측 확인 사항:
MirrorTestDisplaySettings는 빌드의 전체화면 해상도를 맞출 때 기존 Apply를 호출하며
이 호출도 저장을 일으킵니다. 이 SW 호출부는 매니저 연결 방식에 맞춰 조정하겠습니다.

5. 최종 Act 종료 시 런 크레딧의 개인 프로필 이월

사용자 정책은 마지막 Act에서만 아이템을 정리하고, 패시브 구매와 공용으로 쓰는
크레딧은 가지고 나오는 것입니다. 다음 Act가 있으면 런 상태와 미수령 보상을
그대로 유지해야 합니다.

현재 런 지갑과 PlayerProfileData.gold는 별개 상태입니다.
TransferRunGoldToProfile(profile)는 런 지갑을 프로필에 더하고 지갑을 0으로 만들지만
저장하지 않습니다. SaveSinglePlayerSlot은 별도 void 호출이며, 완료 런 식별자와
이미 이월한 기록을 저장하는 경계가 없습니다. Mirror 결과 복귀에는 이월 호출이
연결되어 있지 않습니다. 현재 Act1 테스트 완료를 정식 마지막 Act 청산으로
간주하면 안 됩니다.

최소 요청:
- 참가자 본인의 프로필과 완료 런 ID를 지정해 한 번만 정산하는 저장 경계.
- 저장 성공 여부와 실패 후 재시도 결과를 확인할 수 있는 반환값.
- 프로필 저장과 런 지갑 정리가 어긋나도 중복 지급·유실 없이 복구되는 처리.
- 최종 Act 판정은 런 진행 소유자가 전달하고, 다음 Act 전환에서는 정산하지 않기.

SW에서 임의의 별도 영구 지갑이나 저장 매니저를 추가하지 않았습니다. 이 항목은
코드 경계 확인 결과이며, 저장 실패·프로세스 재시작 복구를 검증한 결과는 아닙니다.

6. 검증 범위

위 결과는 실제 Unity에서의 경로 조회와 별도 컴포넌트의 실패 조건 검사,
원본 호출 흐름 확인을 합친 것입니다. 두 EXE의 실제 동시 파일 쓰기 충돌,
손상 JSON 파일의 로드, 독립 PC 간 설정 저장까지 완료한 결과는 아닙니다.

재현 권장 조건:
별도 테스트 사용자 또는 격리 환경에서 persistentDataPath가 기존 사용자 저장과
다른지 확인한 뒤, 서로 다른 --mirror-profile의 두 EXE로 설정 변경·재시작과
패시브 구매·재로드를 비교해 주세요.
